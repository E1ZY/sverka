# Сверка отчётности по первичным документам

Локальный MVP для проверки карточки фактических затрат КФЗ. Приложение извлекает показатели отчёта и первичных документов, исключает дубли и нерелевантные операции, рассчитывает ожидаемые суммы и показывает доказательства. В предоставленном комплекте оно обнаруживает завышение статьи 0800 на **12 500,00 ₽**.

У каждой проверки есть постоянный ID. В списках показываются первые 8 символов, а на странице проверки и в подтверждении удаления — полный идентификатор. Поиск принимает полный ID и его часть независимо от регистра. ID сохраняется при пересчёте и отображается также у ранее созданных проверок.

## Работа со сверками и документами

- **Проверки** — центральная таблица с ID, названием, типом, временем последнего изменения статуса, статусом и пользователем. Дублирующий список в боковой панели убран. Для старых записей без сохранённого времени изменения статуса показывается прочерк. Вход пока общий, поэтому пользователь обозначен как «Общий доступ».
- Нажатие на название сверки открывает сохранённый отчёт. Кнопка **«Новый отчёт»** в столбце действий открывает форму с теми же документами и параметрами: **1 — главный отчёт, 2 — отчётные документы, 3 — параметры сверки**. Файлы можно удалять по одному, список отчётных документов можно очистить целиком, новые файлы добавляются к выбранным. Запуск из этой формы создаёт новую сверку с новым ID. Прежний комплект, результат и история сохраняются. До запуска новой сверки изменения остаются только в форме.
- **Пакет документов** в строке таблицы или внутри завершённой сверки скачивает ZIP: загруженные оригиналы, сводку CSV и полный результат JSON с деревьями и решениями по документам.
- **Документы** в боковом меню — общий реестр оригиналов и связанных сверок с поиском. Одинаковые файлы объединяются по SHA-256, связи со всеми сверками сохраняются. При удалении сверки можно снять отметку «Также удалить документы, не участвующие в других сверках»: такие оригиналы останутся в реестре. Кнопка **«Удалить без сверок»** удаляет только документы без связей после подтверждения.
- **Деревья затрат** в результатах показывают заявленные и подтверждённые суммы в общей структуре: этап → категория → подкатегория с номером → период. Для отображения используется PrimeReact TreeTable с окраской строк по статусу. Можно переключать отдельные деревья и сравнение, разворачивать ветви и оставлять только проблемы. Показываются годы только проверяемого этапа; справочные другие этапы не добавляются в дерево и не входят в суммы. Зелёный статус «Обосновано» имеет вес 1; жёлтые «Непроверено» и «Не распределено» — 2; красное доказанное расхождение — 3. Родителю передаётся самый строгий статус потомка. Отсутствие данных не считается доказанным расхождением; причина видна под статусом строки.
- **Дополнительные проверки** — обычная таблица: вид проверки, документ или статья, результат и пояснение. В ней собраны дубликаты, отклонения документов, пропуски и статьи вне расчёта; источник можно открыть по ссылке в строке.
- **Дерево отчётности** группирует входящие документы по статье и периоду. В последнем столбце каждого документа указаны **«Принято» / «Отклонено» и причина**. Есть фильтры решений и раскрытие признаков: договор, период, стороны, сумма, номер и статья. Дубликаты, документы другого договора, документы вне периода и неразрешённые документы не входят в подтверждённые затраты. Те же решения сохраняются в журнале.
- **Метаданные карточки** — отдельная таблица извлечённых полей со ссылками на исходную страницу. Не найденные значения остаются пустыми, неуверенное распознавание отмечается для проверки. Стороны карточек сравниваются в одинаковых ролях; исполнитель поставщика в акте не приравнивается к исполнителю основной карточки. Если распределение зарплаты или взносов по подкатегориям не подтверждено, оно не выдумывается: документы показываются отдельной веткой «без разбивки», а итог остаётся частичным.

По умолчанию дерево содержит только год выбранного периода сверки. Галочка **«Показать периоды вне проверки»** добавляет остальные распознанные годы этого этапа: такие строки серые и имеют статус «Вне проверки». Итоги дерева пересчитываются для выбранного представления; скрытые годы в них не входят. В полном представлении неподтверждённые годы не становятся зелёными от совпадения сумм за выбранный период. Переключение читает сохранённый результат и не запускает OCR заново. Полное подтверждение сумм за выбранные месяцы не означает подтверждение всех годов и подкатегорий этапа. Для старых сверок нажмите **«Пересчитать»**, если годовые строки карточки ещё не были извлечены. При обновлении приложения новые таблицы и поле времени изменения статуса добавляются в БД без очистки существующих данных.

## Установка и первый запуск

Выберите один маршрут и проходите его последовательно. В каждом отдельно описаны установка Git, авторизация GitHub, клонирование и запуск:

1. **[Windows без Docker](#1-сборка-и-запуск-без-docker-на-windows)** — раздел 1: команды выполняются в PowerShell, копия проекта хранится, например, в `D:\Coding\sverka`. Python работает на вашем компьютере, данные хранятся в SQLite; интерфейс собирается через Node.js/npm.
2. **[Docker через WSL 2](#2-запуск-через-docker-desktop-и-wsl-2-с-нуля)** — раздел 2: репозиторий клонируется в Ubuntu, например в `~/projects/sverka`, и оттуда запускаются контейнеры приложения, PostgreSQL и OCR. Понадобятся Ubuntu в WSL и Docker Desktop; Python и Node.js для проекта устанавливаются внутри образа.

В блоках `powershell` команды выполняются в **PowerShell Windows**, в блоках `bash` — в **терминале Ubuntu**. Копируйте команды без символов приглашения вроде `PS>` или `$`. Выполняйте следующий шаг после успешного завершения предыдущего.

## 1. Сборка и запуск без Docker на Windows

Весь маршрут выполняется в **PowerShell Windows**. Этот вариант использует Python 3.12 x64, локальную SQLite и встроенный worker. Node.js/npm нужны для подготовки веб-интерфейса. Системный PostgreSQL и отдельная установка Tesseract на Windows не требуются: OCR работает через Python-пакет `tesserocr` и языковые файлы проекта.

### 1.1. Подготовка: инструменты, GitHub и клонирование

| Инструмент | Версия / назначение |
|---|---|
| Windows PowerShell | Встроенный 5.1 или PowerShell 7; запускает вспомогательные скрипты. |
| Python | **3.12, 64-bit** — версия, на которой проверены закреплённые зависимости проекта. |
| py | Python Launcher или Python Install Manager — для команд `py -3.12` ниже. Необязателен, если запускать Python 3.12 x64 по полному пути. |
| pip и venv | Компоненты Python для установки пакетов и создания отдельного окружения. |
| Node.js | Для новой установки выбирайте **LTS 22 или новее**. Также поддерживается 20.19+. |
| npm | **9 или новее**, устанавливается вместе с Node.js; используется `package-lock.json` версии 3. |
| Git | Нужен для клонирования; при скачивании ZIP необязателен. |

Интернет нужен при установке инструментов, клонировании, загрузке Python/npm-пакетов и первоначальном скачивании OCR-моделей. После подготовки документы обрабатываются локально. Python и Node.js можно установить на шаге 1.3, после получения проекта.

Если копия проекта уже есть в Windows, найдите папку с `README.md`, `requirements.txt`, `compose.yaml` и каталогом `scripts`. Это **корень проекта**. Перейдите в неё и продолжайте с шага 1.2. В примерах ниже новая копия находится в `D:\Coding\sverka`; для существующей папки `D:\Coding\Hackathon` используйте свой путь.

#### Установите Git в Windows

Откройте меню «Пуск», найдите **PowerShell**, запустите обычное окно и проверьте:

```powershell
git --version
```

Если появилась версия, переходите к клонированию. Если команда не найдена, установите Git одним из способов:

- Через WinGet: `winget install --exact --id Git.Git --source winget`.
- Через [официальный установщик Git for Windows](https://git-scm.com/install/windows). В установщике оставьте доступ Git из командной строки и компонент Git Credential Manager.

После установки **закройте PowerShell и откройте новое окно**, затем повторите `git --version`: новое окно получает обновлённый `PATH` — список папок, где Windows ищет команды.

Если команда `winget` тоже не найдена, используйте обычный установщик по ссылке. WinGet поставляется через приложение Microsoft **App Installer / «Установщик приложений»**; [инструкция Microsoft](https://learn.microsoft.com/en-us/windows/package-manager/winget/) описывает его установку.

#### Авторизация GitHub для Git в Windows

Репозиторий приватный. Войдите в GitHub в браузере и откройте [E1ZY/sverka](https://github.com/E1ZY/sverka). Если видите 404, проверьте аккаунт и попросите владельца предоставить доступ; приглашение нужно принять. Одного знания ссылки для приватного репозитория недостаточно.

При первом HTTPS-клонировании Git Credential Manager может открыть окно входа. Выберите вход через браузер и авторизуйтесь **аккаунтом, которому предоставлен доступ**; при необходимости пройдите двухфакторную проверку. Git for Windows включает этот механизм. Подробности — в [инструкции GitHub по авторизации Git](https://docs.github.com/en/get-started/git-basics/caching-your-github-credentials-in-git).

#### Склонируйте проект через PowerShell

Сначала выберите папку, в которой у вас хранятся проекты, и определите её полный путь. Например, это может быть `D:\Coding` или `E:\Projects`. Путь можно скопировать из адресной строки Проводника Windows.

В командах ниже **замените `D:\Coding` своим путём в обеих первых строках**. Сохраните кавычки, особенно если в пути есть пробелы. Внутри выбранной папки Git сам создаст подпапку `sverka`: например, для `E:\Projects` проект окажется в `E:\Projects\sverka`.

Выполните команды в **PowerShell Windows**. Первая создаст папку для проектов, если её ещё нет, вторая перейдёт в неё:

```powershell
New-Item -ItemType Directory -Force 'D:\Coding'
Set-Location 'D:\Coding'
git clone https://github.com/E1ZY/sverka.git
Set-Location '.\sverka'
Get-ChildItem
```

`git clone` скачивает проект и создаёт папку `sverka`. При запросе авторизации выполните вход через браузер, описанный выше, затем дождитесь завершения команды. После `Get-ChildItem` должны быть видны `README.md`, `requirements.txt`, `Dockerfile`, `compose.yaml`, `app`, `frontend` и `scripts`. Дальше выполняйте шаги 1.2–1.7 из этой папки. Общая [инструкция по клонированию GitHub](https://docs.github.com/en/repositories/creating-and-managing-repositories/cloning-a-repository) показывает, где скопировать HTTPS-ссылку.

Частые ошибки:

| Сообщение | Что проверить |
|---|---|
| `git is not recognized` / «git не является командой» | Установку Git и новое окно PowerShell после установки. |
| `Repository not found` | Правильность ссылки, доступ к приватному репозиторию и аккаунт, выбранный при входе Git. |
| `destination path ... already exists` | Папка уже существует. Откройте её и проверьте содержимое или выберите другую папку для новой копии. |

Если репозиторий открывается в браузере, но Git всё равно отвечает `Repository not found`, он может использовать ранее сохранённый другой аккаунт. Проверьте запись GitHub в **Панель управления → Учётные записи пользователей → Диспетчер учётных данных**. Для повторной авторизации можно удалить именно эту сохранённую запись и повторить клонирование; порядок описан в приведённой выше инструкции GitHub по авторизации.

#### Альтернатива для Windows: клонирование через GitHub CLI

GitHub CLI предоставляет команду `gh`: через неё можно войти в GitHub и склонировать приватный репозиторий. Для клонирования также нужен Git из шага выше. Если вы уже скачали проект через `git clone`, переходите к шагу 1.2.

В **PowerShell Windows** проверьте наличие CLI:

```powershell
gh --version
```

Если команда не найдена, установите GitHub CLI:

```powershell
winget install --exact --id GitHub.cli --source winget
```

Без WinGet используйте Windows-установщик `.msi` из [официальных релизов GitHub CLI](https://github.com/cli/cli/releases/latest). После установки **закройте PowerShell и откройте новое окно**, затем повторите `gh --version`.

Войдите аккаунтом, которому предоставлен доступ к [E1ZY/sverka](https://github.com/E1ZY/sverka):

```powershell
gh auth login --hostname github.com --git-protocol https --web
```

CLI покажет одноразовый код и откроет браузер. Введите код на указанной странице и завершите вход; при вопросе об авторизации Git подтвердите её. Затем проверьте аккаунт, настройте Git и убедитесь, что репозиторий доступен:

```powershell
gh auth status
gh auth setup-git --hostname github.com
gh repo view E1ZY/sverka
```

После успешной проверки склонируйте проект. **Замените `D:\Coding` своим путём в обеих первых строках**:

```powershell
New-Item -ItemType Directory -Force 'D:\Coding'
Set-Location 'D:\Coding'
gh repo clone E1ZY/sverka
Set-Location '.\sverka'
Get-ChildItem
```

`gh repo clone E1ZY/sverka` создаст подпапку `sverka` в выбранном каталоге. Продолжайте с шага 1.2 из этой папки. Если `gh repo view` или клонирование сообщает об отсутствии доступа, проверьте аккаунт через `gh auth status`, принятие приглашения и повторите вход нужным аккаунтом. Справочники: [`gh auth login`](https://cli.github.com/manual/gh_auth_login) и [`gh repo clone`](https://cli.github.com/manual/gh_repo_clone).

#### Альтернатива для Windows: ZIP через браузер

Откройте репозиторий под аккаунтом с доступом, нажмите **Code → Download ZIP**, распакуйте архив и откройте полученную папку. ZIP достаточно для сборки и запуска; для него Git не обязателен. Если после распаковки внутри находится ещё одна папка `sverka-main`, корнем проекта будет она — там, где лежит `compose.yaml`.

### 1.2. Сначала проверьте установленные инструменты

В **PowerShell**, из корня проекта:

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\scripts\check_dependencies.ps1
```

Скрипт работает даже без Python. Он отдельно проверяет наличие `py` в `PATH` и запуск `py -3.12 --version`, показывает версии и пути к Python, pip, Node.js и npm, проверяет доступность `venv`, а для отсутствующих или неподходящих инструментов выводит подсказки по установке. `OK` означает успешную проверку, `ERROR` — проблему, которую нужно исправить, `WARN` — необязательный компонент. Отсутствующий или неработающий `py` даёт `WARN`: при наличии подходящего Python можно использовать его полный путь. Код завершения `0` означает, что обязательные проверки прошли, `1` — есть ошибки. С флагом `-Project` проверяется именно Python из `.venv` этого проекта: работающий глобальный Python не маскирует сломанное окружение. Параметр `-PythonExe` выбирает интерпретатор только в базовом режиме проверки инструментов.

Проверка ничего не устанавливает, не скачивает и не меняет системные настройки. Базовый режим проверяет **инструменты сборки**; готовность самого проекта проверяется флагом `-Project` на шаге 1.7. Скрипт сначала использует существующую `.venv`, затем ищет установленный Python. При необходимости путь можно указать явно:

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\scripts\check_dependencies.ps1 -PythonExe 'C:\путь\к\python.exe'
```

В последнем примере замените путь своим. Для машинного отчёта есть флаг `-Json`.

### 1.3. Если инструментов нет: установите их

**Python.** При наличии WinGet выполните в PowerShell:

```powershell
winget install --exact --id Python.Python.3.12
```

Можно использовать [официальную страницу Python для Windows](https://www.python.org/downloads/windows/): выбирайте Python **3.12 x64**, а в обычном установщике оставьте включёнными `pip`, launcher и добавление Python в `PATH`. Описание установщиков и launcher есть в [документации Python 3.12](https://docs.python.org/3.12/using/windows.html). Если используется новый Python Install Manager, установите нужную версию командой `py install 3.12` и затем проверьте её командой ниже; работа manager описана в [актуальной документации Python для Windows](https://docs.python.org/3/using/windows.html).

После установки откройте **новое окно PowerShell** и проверьте:

```powershell
py -3.12 --version
py -3.12 -m pip --version
```

Ожидается Python `3.12.x`. Если pip отсутствует:

```powershell
py -3.12 -m ensurepip --upgrade
```

Если `py` не найден, включите компонент **Python Launcher** в установщике Python 3.12 либо установите **Python Install Manager**, затем откройте новое окно PowerShell. Если `py` найден, но `py -3.12 --version` сообщает об отсутствии нужной версии, установите Python 3.12 x64 способом выше; для Python Install Manager выполните `py install 3.12`.

Если `python --version` уже показывает **3.12.x**, вместо `py -3.12` можно использовать `python`. Также можно запускать найденный диагностикой интерпретатор по полному пути: например, `& 'C:\путь\к\python.exe' -m venv .venv` вместо команды создания окружения на шаге 1.4. Если команда `python` открывает Microsoft Store, используйте рабочий `py -3.12` или полный путь: сам по себе Store alias ещё не означает установленный Python.

**Node.js и npm.** Установите их одной командой:

```powershell
winget install --exact --id OpenJS.NodeJS.LTS
```

Без WinGet скачайте **Windows Installer (.msi), LTS** с [официального сайта Node.js](https://nodejs.org/en/download). Оставьте включёнными компоненты **npm package manager** и добавление в `PATH`. npm поставляется вместе с Node.js; [инструкция npm](https://docs.npmjs.com/downloading-and-installing-node-js-and-npm/) описывает этот способ установки.

В **новом окне PowerShell** проверьте:

```powershell
node --version
npm.cmd --version
```

Ожидаются Node.js `22.x` или новее и npm `9.x` или новее. Уже установленный Node.js `20.19+` тоже подходит. Если npm не найден или версия слишком старая, восстановите/обновите установку Node.js с компонентом npm. ### 1.5.1. Xiaomi-OCR-0 вместо Tesseract (необязательно)

Проект поддерживает локальную модель [Xiaomi-OCR-0](https://huggingface.co/xiaomi-research/Xiaomi-OCR-0). Модель подключается к распознаванию сканов, изображений, строк и ячеек КФЗ, включая предварительное извлечение параметров отчёта. DOCX, XLSX и доступный текстовый слой PDF читаются напрямую.

В **PowerShell из корня проекта**, для NVIDIA GPU с подходящим драйвером сначала установите CUDA-сборку PyTorch, затем дополнительные зависимости:

```powershell
.\.venv\Scripts\python.exe -m pip install torch==2.14.0 torchvision==0.29.0 --index-url https://download.pytorch.org/whl/cu130 -c constraints.txt
.\.venv\Scripts\python.exe -m pip install -r requirements-xiaomi-ocr.txt -c constraints.txt
.\.venv\Scripts\python.exe scripts/setup_xiaomi_ocr.py --device cuda
```

Если NVIDIA GPU нет, используйте CPU (распознавание будет медленнее):

```powershell
.\.venv\Scripts\python.exe -m pip install torch==2.14.0 torchvision==0.29.0 --index-url https://download.pytorch.org/whl/cpu -c constraints.txt
.\.venv\Scripts\python.exe -m pip install -r requirements-xiaomi-ocr.txt -c constraints.txt
.\.venv\Scripts\python.exe scripts/setup_xiaomi_ocr.py --device cpu
```

Первичная установка скачивает несколько гигабайт пакетов и весов. Скрипт закрепляет версию модели, сохраняет веса в `.runtime/models/xiaomi-ocr-0`, запускает проверку распознавания контрольной суммы и только после её успеха включает `OCR_PROVIDER=xiaomi` в `.env`. Настройки входа и БД сохраняются. Синтетический проверочный скан и результат находятся в `.runtime/xiaomi-smoke.png` и `.runtime/xiaomi-smoke-result.json`. Для подготовки только весов есть `--download-only`: он не меняет выбранный движок.

Перезапустите сервер через `scripts/start.ps1`. Модель загружается один раз на процесс при первом распознавании; последующие запросы используют её повторно. Документы обрабатываются на этом компьютере, сетевой OCR API не используется. Для существующей сверки нажмите «Пересчитать»: смена движка автоматически сбрасывает кэш извлечённых данных, а прежние результаты запусков сохраняются. В JSON результата сохраняются движок, версия весов и настройки устройства, чтобы можно было установить, чем выполнено распознавание.

Обработка КФЗ включает много отдельных чтений таблицы и может занимать несколько минут, особенно на CPU и при первой загрузке модели. Во время обработки показываются текущий шаг, год и номер ячейки; общий процент учитывает все документы комплекта. Распознаются годовые строки выбранного этапа, реквизиты читаются один раз. Повторное чтение числовой ячейки выполняется, если первое не дало корректного числа или содержит неуверенно распознанный текст. Отсутствующие значения остаются неизвестными.

Длительность сохраняется для каждого нового запуска и видна в списке сверок, открытом отчёте и истории. Во время обработки счётчик обновляется автоматически. Измерение начинается, когда worker берёт задание, и заканчивается при завершении или ошибке: ожидание в очереди не входит, а повторные попытки после прерывания входят. Для старых запусков без измерения в списке показано «—».

Для реального замера всего учебного комплекта на работающем локальном сервере без авторизации:

```powershell
.\.venv\Scripts\python.exe scripts/benchmark_demo.py --runs 2 --output .runtime/demo-benchmark.json
```

Скрипт создаёт отдельную сверку с исходными файлами для каждого прогона, ждёт завершения, сохраняет время сервера, время ожидания результата клиентом, сведения об OCR и показания `nvidia-smi`. Кэш извлечённых документов предыдущей сверки не используется. Первый прогон после перезапуска сервера включает загрузку модели; второй использует загруженную модель, повторно распознавая файлы. На время замера дождитесь окончания других проверок.

Контрольный замер 14.11.2026: Windows, NVIDIA GeForce RTX 4060 Laptop GPU (8 ГБ), PyTorch 2.14.0+cu130, Xiaomi-OCR-0 на CUDA, стандартные ядра PyTorch без `causal_conv1d` и `flash-linear-attention`. В каждом варианте выполнен один полный прогон 23 файлов:

| Условия | Время обработки | До получения результата клиентом |
| --- | ---: | ---: |
| Первый запуск после перезапуска сервера, включая загрузку и прогрев модели | 218,87 с | 219,91 с |
| Модель уже загружена, документы распознаны заново | 117,41 с | 118,32 с |

Оба результата совпали с эталоном исходного комплекта по всем пяти показателям: расхождение по итогу 12 500,00 ₽, учтены 19 первичных документов, ошибок распознавания нет. Полный журнал локального замера: `.runtime/xiaomi-gpu-benchmark.json`.

Tesseract используется для привязки совпадающих слов к координатам. Если точное совпадение не найдено, источник привязан ко всему переданному фрагменту. Оценка уверенности Xiaomi вычисляется из вероятностей сгенерированных токенов и служит эвристикой проверки, а не гарантией правильности числа. Ошибка модели или обрезанный ответ показываются как ошибка распознавания; незаметного переключения на Tesseract нет.

Для возврата к прежнему движку:

```powershell
.\.venv\Scripts\python.exe scripts/setup_xiaomi_ocr.py --disable
```

Затем перезапустите сервер. Веса останутся на диске, повторно скачивать их не придётся. При ошибке CUDA проверьте `nvidia-smi` и команду `.\.venv\Scripts\python.exe -c "import torch; print(torch.cuda.is_available())"`; для CPU повторите настройку с `--device cpu`.

Для **Docker через WSL** веса также готовятся на хосте. В терминале Ubuntu из корня проекта можно создать отдельное небольшое окружение только для скачивания:

```bash
python3 -m venv .runtime/model-download-env
.runtime/model-download-env/bin/python -m pip install huggingface_hub==1.33.0

OCR_PROVIDER=xiaomi XIAOMI_OCR_DEVICE=cpu INSTALL_XIAOMI_OCR=true docker compose up --build -d --wait
```

Compose подключает `.runtime/models` в контейнеры только для чтения. Флаг `INSTALL_XIAOMI_OCR` добавляет зависимости в образ; обычная сборка оставляет Tesseract. Приведённая команда использует CPU. Для последующих пересозданий контейнеров сохраняйте эти три значения в `.env` или повторяйте префикс команды. GPU в контейнер автоматически не передаётся; CUDA-образ также требует настройки GPU-доступа Docker. Локальный Windows-запуск выше использует GPU напрямую.

Дополнительная проверка ищет `.venv`, сверяет Python-пакеты с `requirements.txt`, выполняет `pip check`, проверяет загрузку библиотек/DLL, инициализацию OCR с `rus+eng` и наличие собранного интерфейса. При `ERROR` выполните указанную подсказку и повторите проверку.

Для разработки на своём компьютере выберите `1`: приложение сразу откроет рабочее пространство. При выборе `2` команда дважды запросит пароль не менее 12 символов без отображения ввода и сохранит только его хеш в `.env`. `--http` разрешает вход с паролем по локальному HTTP; для внешнего сайта с HTTPS запускайте настройку без этого флага. Выбранный режим сохраняется между запусками. Подробнее — в разделе [«Вход и доступ к приложению»](#вход-и-доступ-к-приложению).

```powershell

.\.venv\Scripts\python.exe scripts/configure_auth.py --mode local
# Или общий пароль для локального HTTP
.\.venv\Scripts\python.exe scripts/configure_auth.py --mode password --http
```

Запуск из корня проекта:

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\scripts\start.ps1
```

Сначала `start.ps1` проверяет, что Python из `.venv` действительно запускается, использует окружение этого проекта и имеет версию 3.12 x64. Его путь и версия выводятся в терминал. При неработающем окружении запуск прекращается до сборки интерфейса с подсказкой по восстановлению.

Затем скрипт проверяет настройки доступа. Если режим ещё не настроен, в обычном терминале он предложит выбрать его; повторно выбирать режим и вводить пароль при следующих запусках не потребуется. При запуске без интерактивного терминала сначала настройте режим явной командой выше.

`start.ps1` перед запуском сравнивает содержимое исходников, стилей, ресурсов и настроек интерфейса с последней успешной сборкой. Если файлы изменены, добавлены или удалены либо готовая сборка отсутствует или повреждена, скрипт выполняет `npm.cmd run build` из `frontend`. Если сборка актуальна, пересборка пропускается и npm не требуется. При ошибке сборки сервер не запускается: исправьте указанную ошибку и повторите запуск. Первый запуск обновлённого скрипта также пересобирает интерфейс один раз, чтобы сохранить его состояние.

`-ExecutionPolicy Bypass` действует только для запущенного процесса PowerShell. Если запуск `.ps1` в вашей системе разрешён, достаточно `.\scripts\start.ps1`. Альтернатива напрямую через Python (без автоматической пересборки интерфейса):

```powershell
.\.venv\Scripts\python.exe -m uvicorn app.main:app --host 127.0.0.1 --port 8000
```

Оставьте терминал работающим и откройте в браузере Windows **http://127.0.0.1:8000**. Проверка готовности API: **http://127.0.0.1:8000/api/health**, документация API: **http://127.0.0.1:8000/docs**. В интерфейсе откройте «Примеры проверок» и запустите исходный комплект или «Проверить все примеры (31)».

Остановка — **Ctrl+C** в терминале сервера. Следующий запуск — та же команда `start.ps1`; повторная установка пакетов не нужна. Документы и SQLite хранятся в `data/`. Для этого режима используйте один API-процесс, без `--workers` и `--reload`.

Затем обновите страницу через **Ctrl+F5**. Если изменились `package.json` или `package-lock.json` в `frontend`, перед запуском обновите npm-зависимости командой `npm.cmd --prefix frontend ci` из корня проекта. Папка `frontend/dist` не хранится в Git; её актуальность при запуске обеспечивает `start.ps1`.

**Ошибка `No Python at ...` при существующей `.venv`**

Скрипт использует `.venv/Scripts/python.exe`, но это окружение зависит от базового Python, на котором его создали. Путь к нему записан в `.venv/pyvenv.cfg`. Если базовый Python удалён или перемещён, файл `python.exe` в окружении остаётся, но не запускается. Активация `.venv` эту ссылку не исправляет.

Установите обычный Python 3.12 x64 по шагу 1.3. Для восстановления окружения, уже созданного на **Python 3.12 x64**, выполните из корня проекта:

```powershell
py -3.12 --version
py -3.12 -m venv --upgrade .venv
.\.venv\Scripts\python.exe -m pip check
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\scripts\check_dependencies.ps1 -Project
.\scripts\start.ps1
```

`--upgrade` обновляет связь с установленным Python и сохраняет пакеты в `.venv`. Если `py` недоступен, используйте полный путь к установленному Python 3.12 вместо `py -3.12`. Проверьте результат командой:

```powershell
.\.venv\Scripts\python.exe -c "import sys; print('Python проекта:', sys.executable); print('Базовый Python:', sys.base_prefix)"
```

Первая строка должна указывать на `.venv\Scripts\python.exe` внутри проекта, вторая — на установленный Python. Для постоянной установки используйте установленный Python, а не временный интерпретатор из поставки среды разработки. Если окружение было создано на другой версии Python или с другой разрядностью, переименуйте старую папку `.venv` и создайте новое окружение по шагу 1.4. Если диагностика обнаружила недостающие пакеты, повторите установку из `requirements.txt` с `constraints.txt`.

Для разработки интерфейса можно запустить API на порту 8000 и `npm.cmd run dev` из `frontend`: Vite проксирует `/api` в локальный backend. Для обычного использования достаточно production-сборки выше.

## 2. Запуск через Docker Desktop и WSL 2 с нуля

**WSL** позволяет работать с Ubuntu внутри Windows. **Docker Desktop** запускает контейнеры и предоставляет команду `docker` этой Ubuntu. **Docker Compose** по файлу `compose.yaml` поднимает три сервиса проекта: `db` (PostgreSQL 16), `api` (приложение) и `worker` (обработка документов). Python, Node.js/npm и OCR устанавливаются внутри образов при сборке.

Этот маршрут можно пройти самостоятельно, начиная с установки WSL. Git и авторизация GitHub настраиваются внутри Ubuntu; новая копия проекта будет находиться в `~/projects/sverka`. Для Linux-команд используйте терминал Ubuntu, для установки WSL и Docker Desktop — Windows, как указано в каждом шаге.

Для Docker Desktop нужны поддерживаемая версия Windows, WSL 2, включённая аппаратная виртуализация и как минимум **8 ГБ системной RAM**; актуальные требования приведены на [официальной странице установки](https://docs.docker.com/desktop/setup/install/windows-install/). Для первой сборки нужен интернет и место на диске под Linux, образы и зависимости.

Состояние виртуализации можно посмотреть в Windows: **Ctrl+Shift+Esc → Производительность → ЦП → Виртуализация**. Если она отключена, включите VT-x / AMD-V в BIOS/UEFI по инструкции производителя компьютера.

### 2.1. Установите Ubuntu в WSL

В Windows откройте **PowerShell от имени администратора**: «Пуск» → PowerShell → «Запуск от имени администратора».

```powershell
wsl --install -d Ubuntu
```

Дождитесь завершения и **перезагрузите Windows**, если это предложено. Затем откройте **Ubuntu** из меню «Пуск». При первом запуске создайте Linux-пользователя и пароль; при вводе пароля символы не отображаются — это нормально. Этот пользователь относится к Ubuntu.

Снова в **PowerShell Windows**:

```powershell
wsl --update
wsl --list --verbose
```

В таблице рядом с Ubuntu должна быть `VERSION 2`; `Stopped` в колонке состояния допустим, когда терминал закрыт. Если указана версия 1:

```powershell
wsl --set-version Ubuntu 2
```

Подставьте точное имя из колонки `NAME`, если оно отличается, например `Ubuntu-24.04`. Установка и команды описаны в [руководстве Microsoft по WSL](https://learn.microsoft.com/en-us/windows/wsl/install) и [справочнике команд WSL](https://learn.microsoft.com/en-us/windows/wsl/basic-commands).

### 2.2. Установите и настройте Docker Desktop

### 2.8. Настройте окружение и соберите контейнеры

Выполните команды **в Ubuntu, из корня проекта** — подойдёт и встроенный терминал VS Code, подключённый к WSL. Создайте `.env` из примера, сохранив существующий файл, если он уже есть:

```bash
if [ ! -f .env ]; then cp .env.example .env; fi
python3 scripts/configure_auth.py --http
docker compose config --quiet
docker compose up --build -d --wait
docker compose ps
```

На шаге `configure_auth.py` выберите **1 — без авторизации для локальной разработки** или **2 — с общим паролем**. Для варианта `2` задайте пароль не менее 12 символов. Вместо меню можно выполнить `python3 scripts/configure_auth.py --mode local` либо `python3 scripts/configure_auth.py --mode password --http`. В локальном режиме используйте адрес Windows `http://127.0.0.1:8000`; внешний IP и имя компьютера не принимаются.

`.env` задаёт пароль PostgreSQL и настройки входа в приложение. `configure_auth.py` сохраняет существующий пароль БД. Пароль PostgreSQL можно изменить **до первого запуска**; используйте URL-safe символы, например латинские буквы и цифры. Существующий пароль уже созданной БД не изменяется простым редактированием `.env`.

`--build` собирает образ, `-d` оставляет контейнеры работать в фоне, `--wait` ждёт их готовности. Первая сборка может занять несколько минут: скачиваются базовые образы, Python/npm-пакеты и OCR-компоненты. После успешного завершения в `docker compose ps` сервисы `db` и `api` должны быть healthy, а `worker` — запущен. Команда описана в [справочнике Docker Compose](https://docs.docker.com/reference/cli/docker/compose/up/).

### 2.9. Откройте приложение в Windows: порт уже опубликован

В `compose.yaml` у сервиса `api` уже настроено сопоставление порта:

```yaml
ports:
  - "${BIND_ADDRESS:-127.0.0.1}:8000:8000"
```

Формат записи — `адрес хоста:порт хоста:порт контейнера`. Значение `BIND_ADDRESS` берётся из `.env`; если переменная отсутствует или пуста, используется `127.0.0.1`. В `.env.example` также задан локальный адрес. При выбранном в этом гайде Docker Desktop с WSL 2 порт 8000 контейнера доступен на `127.0.0.1:8000` Windows. Docker Desktop перенаправляет запросы с Windows в контейнер — это описано в [документации по публикации портов](https://docs.docker.com/desktop/features/networking/#how-exposed-ports-work). Внутри контейнера Uvicorn слушает `0.0.0.0:8000`; по умолчанию доступ с хоста ограничен этим компьютером. Для внешнего доступа меняйте только `.env` по разделу [«Внешний доступ через .env»](#внешний-доступ-через-env).

В обычном **браузере Windows** откройте:

- **http://127.0.0.1:8000** — интерфейс;
- **http://127.0.0.1:8000/api/health** — проверка API, поле `status` должно быть `ok`;
- **http://127.0.0.1:8000/docs** — Swagger API.

Compose запускает сервисы; страницу в браузере откройте вручную после завершения сборки. Проверить соединение из **PowerShell Windows** можно так:

```powershell
Invoke-RestMethod http://127.0.0.1:8000/api/health
```

В ответе должно быть `status: ok`. Если страница недоступна, в терминале Ubuntu проверьте `docker compose ps` и `docker compose logs --tail=100 api`; сервис `api` должен быть healthy.

Нажмите «Примеры проверок» → «Исходный комплект задания» → «Запустить проверку» или «Проверить все примеры (31)». При дальнейшей работе оставляйте Docker Desktop запущенным; терминал Ubuntu после запуска с `-d` можно закрыть.

## Вход и доступ к приложению

Режим выбирается при установке командой `scripts/configure_auth.py --http` и сохраняется в `.env`. Первый запуск `start.ps1` тоже предлагает выбор, если доступ ещё не настроен:

| Режим | Поведение | Явная команда настройки |
|---|---|---|
| `local` | Без формы входа и кнопки «Выйти», только через `localhost` / `127.0.0.1` / `::1` | `python scripts/configure_auth.py --mode local` |
| `password` | Форма с общим паролем рабочего пространства | `python scripts/configure_auth.py --mode password --http` для локального HTTP; без `--http` для HTTPS |

В Windows используйте `.\.venv\Scripts\python.exe` вместо `python`, в Ubuntu — `python3`. После изменения режима перезапустите локальный сервер; в Docker выполните `docker compose up -d --wait --no-deps --force-recreate api`. При первом обновлении до версии с выбором режима сначала пересоберите образ: `docker compose up --build -d --wait`.

В `local` пароль не требуется, прежний хеш удаляется из `.env`, а `BIND_ADDRESS` устанавливается в `127.0.0.1`. Проверяются локальное имя сайта и адрес подключения; изменяющие запросы требуют заголовок `X-Sverka-Request: 1`, который интерфейс добавляет автоматически. Docker допускает подключение через внутренний bridge при локальной публикации порта. Сочетание `AUTH_MODE=local` с внешним `BIND_ADDRESS` останавливает запуск API с подсказкой. Для сетевого доступа выберите `password`.

В `password` все вошедшие пользователи видят одни и те же проверки и документы. Регистрации и отдельных личных кабинетов нет.

Если `AUTH_MODE` не задан, используется `password`: без настроенного пароля данные остаются закрытыми, интерфейс показывает инструкцию по выбору режима, защищённые API возвращают `503`. В режиме с паролем без действующей сессии API, оригиналы и изображения документов, экспорт, учебные архивы и Swagger возвращают `401`. Публичными остаются оболочка страницы входа, её ресурсы, `/api/auth/session`, `/api/auth/login` и `/api/health`.

Для Ubuntu-сервера с уже работающими контейнерами:

```bash
cd ~/apps/sverka &&
git pull --rebase --autostash &&
python3 scripts/configure_auth.py --mode password &&
docker compose build api &&
docker compose up -d --wait --no-deps --force-recreate api worker
```

Команда настройки запросит новый пароль дважды и сохранит в `.env` только PBKDF2-HMAC-SHA256 с отдельной случайной солью и 600 000 итераций. Существующие настройки, включая пароль PostgreSQL, сохраняются. Пароль не передаётся как аргумент команды и не попадает в историю shell. `.env` исключён из Git. `--autostash` сохраняет и возвращает локальные изменения перед получением обновления; если Git сообщит о конфликте, разрешите его перед сборкой. В старых версиях Git `--autostash` поддерживается только вместе с `--rebase`, поэтому используется эта комбинация. Связка `&&` останавливает последовательность при ошибке: если обновление не скачалось, настройка и сборка старой версии не запускаются.

По умолчанию `AUTH_COOKIE_SECURE=true`: вход рассчитан на HTTPS. Обратный прокси должен направлять и интерфейс, и `/api` на приложение. Оставляйте Docker-порт на loopback и публикуйте наружу HTTPS-прокси. Пароль и cookie при обычном HTTP передаются без шифрования: форма входа этого не исправляет. HTTPS и ограничения IP по-прежнему нужны для реальных документов.

Для localhost или доступа через SSH-туннель выполните настройку с `--http`:

```bash
python3 scripts/configure_auth.py --mode password --http
docker compose up -d --wait --no-deps --force-recreate api
```

Этот режим устанавливает `AUTH_COOKIE_SECURE=false`. Для временной демонстрации по внешнему HTTP-IP он технически работает, но используйте только учебные документы и ограничивайте IP участников в firewall хостинга. Чтобы вернуться к HTTPS-режиму, повторите настройку без `--http` и пересоздайте `api`.

При запуске напрямую через Python настройки входа также читаются из `.env`; переменные окружения имеют приоритет. После смены пароля перезапустите Python-сервер или пересоздайте контейнер `api`. Смена пароля завершает все предыдущие сессии. Пароль можно сменить той же командой, поэтому отдельной функции восстановления через почту нет.

Вход сохраняется в `HttpOnly; SameSite=Strict` cookie на 12 часов, а в БД хранится только хеш случайного идентификатора сессии. В HTTPS-режиме cookie также имеет `Secure`. Кнопка «Выйти» удаляет сессию на сервере, поэтому её скопированная cookie больше не работает. Для изменяющих запросов требуется привязанный к сессии CSRF-токен; форма входа использует JSON и отдельный заголовок. Cookie и CSRF-токен не сохраняются в localStorage.

В текущем однопроцессном API Compose разрешено до 5 попыток входа с одного адреса за 5 минут и до 60 попыток суммарно за минуту. Лимиты находятся в памяти процесса; перезапуск их сбрасывает. Для нескольких API-процессов нужен общий limiter или ограничение на HTTPS-прокси. Защита входа не задаёт квоты на обработку документов для пользователей, которым известен пароль.

## Внешний доступ через .env

Адрес публикации Docker задаётся переменной `BIND_ADDRESS` в `.env` рядом с `compose.yaml`. Сам `compose.yaml` редактировать не нужно. `.env` исключён из Git, поэтому выбранный режим доступа сохраняется при `git pull`. Не заменяйте существующий `.env` целиком файлом `.env.example`: в нём уже сохранены пароль PostgreSQL и хеш пароля входа.

| Значение в `.env` | Доступ |
|---|---|
| `BIND_ADDRESS=127.0.0.1` | Только с самого сервера, через SSH-туннель или локальный HTTPS-прокси. Значение по умолчанию. |
| `BIND_ADDRESS=0.0.0.0` | По всем IPv4-интерфейсам сервера, включая внешний IP, на порту 8000. |

Для включения внешнего доступа на Ubuntu-сервере после получения обновления:

```bash
cd ~/apps/sverka
nano .env
```

Добавьте строку `BIND_ADDRESS=0.0.0.0` или измените уже существующее значение. Сохраните файл: Ctrl+O → Enter → Ctrl+X. Затем примените настройку:

```bash
docker compose config --quiet &&
docker compose up -d --wait --no-deps --force-recreate api &&
docker compose ps api
```

В выводе должно появиться `0.0.0.0:8000->8000/tcp`. Открывайте `http://ВНЕШНИЙ_IP:8000/`; если доступ закрыт в firewall панели хостинга, разрешите входящий TCP-порт 8000 с нужных IP. Перед внешней публикацией настройте пароль по предыдущему разделу. Для реальных документов используйте HTTPS; `AUTH_COOKIE_SECURE=false` нужен только для выбранного HTTP-режима и не шифрует трафик.

Пересобирать образ или перезапускать БД и worker после изменения `BIND_ADDRESS` не требуется. Для возврата к локальному доступу задайте `BIND_ADDRESS=127.0.0.1` и повторите команды применения. Переменная окружения shell с тем же именем имеет приоритет над `.env`; если результат отличается от ожидаемого, выполните `unset BIND_ADDRESS` и повторите применение. Смена пароля через `configure_auth.py` сохраняет `BIND_ADDRESS` и остальные настройки `.env`.

Если раньше вы вручную меняли порт в `compose.yaml`, перед первым обновлением сохраните его копию и верните файл к версии Git. Это разовый переход: после него настраивайте адрес только в `.env`.

```bash
cd ~/apps/sverka &&
mkdir -p .runtime &&
cp compose.yaml ".runtime/compose.before-env.$(date +%Y%m%d-%H%M%S).yaml" &&
git checkout -- compose.yaml &&
git pull --rebase --autostash
```

Копия прежнего файла остаётся в `.runtime`. Если в нём были другие ручные изменения, перенесите нужные настройки отдельно; старую строку публикации порта возвращать не нужно. Остальные локальные изменения Git сохраняет через `--autostash`. После обновления задайте `BIND_ADDRESS` в существующем `.env`. При первом переходе соберите актуальный образ и пересоздайте оба сервиса приложения, чтобы на сервере использовался текущий код, включая авторизацию:

```bash
docker compose build api &&
docker compose up -d --wait --no-deps --force-recreate api worker
```

При последующей смене только `BIND_ADDRESS` достаточно пересоздать `api`, как описано выше. Для последующих обновлений без локальных изменений исходников достаточно `git pull --ff-only` — `.env` Git не меняет. Если обновляется код приложения, пересоберите образ и пересоздайте `api` и `worker` по инструкции обновления.

### 2. Собственный или неполный комплект

Чтобы очистить сохранённые проверки, нажмите **«Очистить»** в центральной таблице. Перед удалением появится предупреждение с количеством проверок и отметкой об удалении документов без других связанных сверок. Для удаления одной проверки используйте корзину в её строке или кнопку удаления внутри открытой проверки: предупреждение покажет её название. «Отмена», крестик и Escape закрывают его без удаления. Если снять отметку об удалении документов, оригиналы сохранятся в общем реестре. Исходные файлы на компьютере сохраняются в любом случае. Выполняющиеся проверки остаются. Очистка охватывает загруженный список проверок независимо от поискового фильтра.

Пока проверок ещё нет, стартовый экран предлагает **«Пройти учебный пример»** на готовом комплекте или **«Загрузить свои документы»**. После появления проверок обучение можно снова открыть по кнопке **«Учебный пример»** в шапке.

Краткий обзор формы доступен по кнопке **«Показать подсказки»** внутри новой проверки. Подсказки по очереди выделят загрузку КФЗ, параметры сверки, первичные документы, полноту комплекта и запуск. Можно заполнять форму во время обучения или пройти шаги без документов. Кнопки «Назад» и «Далее» переключают шаги, Escape закрывает подсказки. Завершение обучения сохраняет заполненные поля и не запускает сверку автоматически.

Отдельная кнопка **«Учебный пример»** запускает практический туториал на готовом комплекте документов. Для ручного выбора скачайте учебный архив прямо из подсказки и распакуйте его: ZIP содержит папки `report` с КФЗ и `primary` с 22 первичными документами. Обучение состоит из 11 шагов: выбор КФЗ, проверка параметров строки, выбор первичных документов, подтверждение полноты, запуск сверки, ожидание расчёта, выбор фильтра расхождений, открытие статьи, просмотр КФЗ, просмотр первичного документа и сравнение сумм. Документы выбираются через ту же форму, что и в обычной проверке. **«Далее» недоступна, пока текущее задание не выполнено**; неверный ответ на последнем шаге также блокирует завершение. При просмотре источника подсветка открывает сам подтверждающий фрагмент, а не заголовок файла. В конце запускается короткая анимация конфетти; кнопка «Ещё конфетти» повторяет её. Можно вернуться назад или выйти через крестик, Escape либо «Выйти» — выход не считается прохождением. Учебная проверка создаётся отдельно и остаётся в списке проверок.

На шагах загрузки кнопки **«Подставить КФЗ примера»** и **«Подставить документы примера»** выбирают один учебный отчёт и 22 первичных документа. Скачивать архив для этого не нужно; ручной выбор файлов из распакованного архива также доступен. Подставленные файлы видны в обычной форме, их можно убрать или заменить. Сверка начинается после подтверждения полноты комплекта и нажатия «Начать сверку».

На шаге параметров кнопка **«Подставить данные примера»** заполняет договор, этап и период учебного комплекта. Значения можно исправить вручную. После подстановки файлов или параметров обучение остаётся на текущем шаге: проверьте данные и нажмите «Далее».

После верного ответа и нажатия **«Завершить обучение»** появляется поздравление с падающим конфетти. Эта короткая анимация работает и при включённом в системе уменьшении движения. Обзор формы из пяти шагов работает как прежде.

В учебном примере скан автоматически приближается к выделенной сумме. В подсказке крупно показаны сумма, этап, год и статья. Панель над документом позволяет менять масштаб, возвращаться **«К фрагменту»** и показывать лист целиком кнопкой **«Вся страница»**. Эти инструменты доступны и при обычном просмотре документов. Предпросмотр PDF загружается в повышенном разрешении, а на узком экране подсказка располагается рядом с выделенной суммой, не закрывая её.

Нажмите «Новая проверка» и выберите отчёт КФЗ (PDF, PNG или JPEG). После выбора файла приложение попробует заполнить номер договора, этап и даты периода. Проверьте найденные значения: любое поле можно исправить вручную. Отсутствующие, неоднозначные или неуверенно распознанные значения остаются пустыми с подсказкой. Ручные правки сохраняются, в том числе если распознавание ещё выполняется или выбран другой отчёт; прежние автоматические значения при замене или удалении КФЗ очищаются.

Даты подставляются только из явно указанного периода (диапазон дат, диапазон месяцев или один месяц), дата договора и один лишь год не используются. Если в КФЗ перечислено несколько разных этапов, выберите нужный вручную. Период сверки должен находиться внутри одного года. Распознавание выполняется локально; временная копия файла удаляется, проверка и задание обработки на этом шаге не создаются. При ошибке распознавания параметры можно заполнить вручную и продолжить.

Добавьте первичные документы PDF/DOCX/XLSX/PNG/JPEG и запустите сверку. В MVP профиль отчёта соответствует предоставленной 17-колоночной форме КФЗ.

Если полнота комплекта не подтверждена, система покажет подтверждённые промежуточные суммы со статусом «Недостаточно данных». Например, при отсутствии январской ведомости по зарплате статья 0200 и итог не будут помечены как ошибочные; ожидаемая полная сумма останется неизвестной. Обработка остальных файлов продолжится.

При наличии неоднозначных распознанных данных откройте документ и выберите «Уточнить данные». Можно изменить статью/сумму с обязательным основанием; API также поддерживает уточнение договора и периода. Создаётся событие аудита и новый запуск. Исходное извлечение и предыдущие результаты сохраняются. Это пользовательское уточнение, а не новое автоматическое доказательство: оно явно отмечается в результате.

## Архитектура и поток данных

```text
React → FastAPI → PostgreSQL / SQLite
                    ↓ постоянное задание Run
                  worker
                    ↓
  извлечение → нормализация → фильтрация → классификация → Decimal-сверка
                    ↓
  неизменяемый снимок результата + ссылки на фрагменты → React / JSON / CSV
```

| Модуль | Назначение |
|---|---|
| `app/main.py` | REST API, загрузки, просмотр оригиналов и страниц, экспорт, аудит уточнений |
| `app/db.py` | Case, Document, Run, Review; схема БД и сессии |
| `app/pipeline.py` | Постоянная очередь, аренда задания, прогресс, кеш извлечения и снимки запусков |
| `app/extractors.py` | PDF-текст и OCR, DOCX-таблицы, XLSX-регистры, профиль сетки КФЗ |
| `app/report_context.py` | Предварительное распознавание договора, этапа и периода КФЗ с проверкой неоднозначности и уверенности OCR |
| `app/ocr.py` | Сменный интерфейс локального OCR: Tesseract или Xiaomi-OCR-0 |
| `app/xiaomi_ocr.py` | Локальная модель Transformers, сериализация запросов и оценки уверенности |
| `app/domain.py` | Чистое расчётное ядро без доступа к файлам, БД и эталону |
| `app/rules.json` | Версия правил классификации, колонки профиля КФЗ, непроверяемые подпоказатели |
| `frontend/src` | Рабочее пространство проверок, детализация расчётов и просмотр доказательств |

Факты и доказательства хранятся структурированным JSON в Document, а операции и расчёты — в снимке Run. Каждый факт имеет источник: нормализованный прямоугольник страницы, Excel-диапазон или DOCX-адрес. Снимок содержит версии пайплайна/правил, контекст, хеши файлов и применённые уточнения. Денежные значения сериализуются строками, расчёт выполняется через Decimal с ROUND_HALF_UP до копейки. Дельта — отчёт минус ожидаемое значение.

Дубли выявляются по SHA-256 и реквизитам: номер, дата, договор, контрагент, сумма. Конфликтующие версии с разными суммами исключаются из подтверждённого агрегата до проверки. Для зарплаты и взносов контролируется наличие единственного расчёта на каждый месяц. Пересечение периода не распределяется пропорционально автоматически.

Отсутствующие данные не превращаются в нули. Ошибка чтения/неоднозначная связь консервативно блокирует полное подтверждение агрегатов, поскольку нераспознанный документ может относиться к любой статье. В итоговом заключении всегда указываются границы проверки.

Тяжёлое извлечение выполняет worker. В PostgreSQL задание выбирается через `FOR UPDATE SKIP LOCKED`; локальный SQLite рассчитан на одного worker. Аренда обновляется при переходе к документу, истекает через 10 минут. Задание после прерывания подбирается повторно, максимум три попытки. Успешные извлечения кешируются; повторный запуск пересчитывает результат из фактов и снимка уточнений. Таблицы создаются автоматически; для последующих изменений схемы понадобятся миграции.

## Настройки

Переменные окружения читаются процессом при старте. Для прямого запуска `.env` автоматически не загружается: задайте переменные в shell. Compose читает `.env`; образец — `.env.example`.

| Переменная | Значение по умолчанию / назначение |
|---|---|
| `DATABASE_URL` | SQLite `data/audit.db`; Compose задаёт PostgreSQL |
| `DATA_DIR` | `data/`; оригиналы и локальная БД |
| `DEMO_DIR` | `task/data`; в контейнере `/demo` |
| `FIXTURES_DIR` | `cases/`; каталог, входные документы и эталоны синтетических кейсов |
| `EMBED_WORKER` | `true` локально; `false` для отдельного worker |
| `TESSDATA_PREFIX` | `.runtime/tessdata` для Windows tesserocr; Linux CLI использует системные модели |
| `TESSERACT_CMD` | Необязательный путь к CLI Tesseract |
| `OCR_PROVIDER` | `tesseract` по умолчанию; `xiaomi` после подготовки модели |
| `XIAOMI_OCR_MODEL` | Локальная папка весов, по умолчанию `.runtime/models/xiaomi-ocr-0` |
| `XIAOMI_OCR_DEVICE` | `auto`, `cuda`, `cpu` или `mps`; в Compose по умолчанию CPU |
| `XIAOMI_OCR_MAX_NEW_TOKENS` | Максимальная длина ответа, по умолчанию 4096; для ячеек лимит уменьшается |
| `XIAOMI_OCR_TIMEOUT` | Лимит генерации в секундах, по умолчанию 180; незавершённый ответ отклоняется |
| `POSTGRES_PASSWORD` | Локальный пароль Compose; при изменении используйте URL-safe символы |
| `AUTH_MODE` | `password` по умолчанию; `local` — без авторизации, только на localhost |
| `AUTH_PASSWORD_HASH` | Хеш общего пароля, создаётся `scripts/configure_auth.py`; в локальном режиме пуст |
| `AUTH_COOKIE_SECURE` | `true` для HTTPS; `false` для входа по локальному HTTP |
| `BIND_ADDRESS` | Адрес публикации Docker, по умолчанию `127.0.0.1`; в режиме `local` только loopback |

Ограничения загрузки: 25 МБ на файл, 100 файлов на проверку, 50 страниц на PDF, распакованный DOCX/XLSX до 100 МБ. Ошибки файлов показываются отдельно. Внешние сервисы, API-ключи, GPU и облачная LLM не требуются.

## Проверки

```powershell
.\.venv\Scripts\python.exe -m pip install -r requirements-dev.txt -c constraints.txt
.\.venv\Scripts\python.exe -m pytest -q
Set-Location frontend
npm.cmd run build
Set-Location ..
```

`requirements-dev.txt` добавляет инструменты тестирования к пакетам приложения. Диагностику сборки можно проверить отдельно командой `.\.venv\Scripts\python.exe -m pytest tests/test_dependency_check.py -q`: её тесты имитируют отсутствующие инструменты, старые версии Node.js/npm и неподходящий Python, не меняя установленные программы. Скрипт проверен в Windows PowerShell 5.1; расширенная проверка `check_dependencies.ps1 -Project` на подготовленном окружении проходит все проверки.

Тесты проверяют полный комплект с OCR и независимым эталоном, точные адреса доказательств, независимость от имён файлов, пропущенный месяц, изменение суммы, повторный скан, конфликт версий, неполный комплект, повреждённый документ, отсутствующее значение отчёта, округление, API, экспорт и сохранение истории уточнений. XLSX с правильными ответами исходного задания используется только в тестах; тесты также проверяют соответствие ему `demo/expected.json`. JSON-эталоны исходного и синтетических кейсов читаются отдельным модулем сравнения после расчёта. Для тестирования полного комплекта нужен исходный каталог `task/data` и доступный локальный OCR.

Последний полный прогон на Windows с Python 3.12: **233 passed, 5 xfailed**, включая тесты диагностики инструментов. Production-сборка TypeScript/Vite успешна. Проверены новая таблица сверок, создание изменённой копии с новым ID, сохранение прежнего результата, ZIP с оригиналами и отчётом, общий реестр со связями, деревья затрат и отчётности, причины отклонений и мобильная навигация. В браузере также проверены неверный и правильный пароль, сохранение входа после обновления страницы, выход и возврат другой вкладки к форме входа после отзыва сессии. В браузере проверены ручная загрузка комплекта и завершение сверки, финансовый итог и фильтры показателей, поиск проверок и документов, каталог кейсов и фильтры общего прогона, управление диалогами с клавиатуры и мобильный экран шириной 390 пикселей. ## Границы MVP

Профиль КФЗ поддерживает данную табличную форму и одну выбранную годовую строку на первой странице. Координаты сетки определяются по изображению, суммы не зашиты в код. Произвольные формы, повёрнутые/перспективно искажённые и низкокачественные сканы требуют дополнительных профилей и предобработки.

XLSX-парсер поддерживает структуры ведомостей/взносов этого набора. Он складывает исходные начисления и не использует пустой или устаревший кеш итоговой формулы. Универсальное вычисление Excel-формул не реализовано. Текстовые документы рассматриваются как одна денежная операция; документы с несколькими различными суммами требуют уточнения. Классификация основана на прозрачных смысловых правилах, сложные случаи получают статус проверки.

Следующие расширения: построчная модель многооперационных актов и УПД, регистры полноты, дополнительные профили КФЗ, дополнительные OCR-профили и калибровка оценок уверенности, авторизация и разграничение доступа, миграции схемы, объектное хранилище. Полнота комплектов и профессиональная оценка бухгалтерского учёта остаются за пользователем.
