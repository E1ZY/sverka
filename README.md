# Сверка отчётности по первичным документам

Локальный MVP для проверки карточки фактических затрат КФЗ. Приложение извлекает показатели отчёта и первичных документов, исключает дубли и нерелевантные операции, рассчитывает ожидаемые суммы и показывает доказательства. В предоставленном комплекте оно обнаруживает завышение статьи 0800 на **12 500,00 ₽**.

## Установка и первый запуск

Выберите один маршрут и проходите его последовательно. В каждом отдельно описаны установка Git, авторизация GitHub, клонирование и запуск:

1. **[Windows без Docker](#1-сборка-и-запуск-без-docker-на-windows)** — раздел 1: команды выполняются в PowerShell, копия проекта хранится, например, в `D:\Coding\sverka`. Python работает на вашем компьютере, данные хранятся в SQLite; интерфейс собирается через Node.js/npm.
2. **[Docker через WSL 2](#2-запуск-через-docker-desktop-и-wsl-2-с-нуля)** — раздел 2: репозиторий клонируется в Ubuntu, например в `~/projects/sverka`, и оттуда запускаются контейнеры приложения, PostgreSQL и OCR. Понадобятся Ubuntu в WSL и Docker Desktop; Python и Node.js для проекта устанавливаются внутри образа.

В блоках `powershell` команды выполняются в **PowerShell Windows**, в блоках `bash` — в **терминале Ubuntu**. Копируйте команды без символов приглашения вроде `PS>` или `$`. Выполняйте следующий шаг после успешного завершения предыдущего.

## 1. Сборка и запуск без Docker на Windows

Весь маршрут выполняется в **PowerShell Windows**. Этот вариант использует Python 3.12 x64, локальную SQLite и встроенный worker. Node.js/npm нужны для подготовки веб-интерфейса. Системный PostgreSQL и отдельная установка Tesseract на Windows не требуются: OCR работает через Python-пакет `tesserocr` и языковые файлы проекта.

### 1.1. Подготовка: инструменты, GitHub и клонирование

| Инструмент | Версия / назначение |
|---|---|
| Windows PowerShell | Встроенный 5.1 или PowerShell 7; запускает вспомогательные скрипты. |
| Python | **3.12, 64-bit** — версия, на которой проверены закреплённые зависимости проекта. |
| py | Python Launcher или Python Install Manager — для команд `py -3.12` ниже. Необязателен, если запускать Python 3.12 x64 по полному пути. |
| pip и venv | Компоненты Python для установки пакетов и создания отдельного окружения. |
| Node.js | Для новой установки выбирайте **LTS 22 или новее**. Также поддерживается 20.19+. |
| npm | **9 или новее**, устанавливается вместе с Node.js; используется `package-lock.json` версии 3. |
| Git | Нужен для клонирования; при скачивании ZIP необязателен. |

Интернет нужен при установке инструментов, клонировании, загрузке Python/npm-пакетов и первоначальном скачивании OCR-моделей. После подготовки документы обрабатываются локально. Python и Node.js можно установить на шаге 1.3, после получения проекта.

Если копия проекта уже есть в Windows, найдите папку с `README.md`, `requirements.txt`, `compose.yaml` и каталогом `scripts`. Это **корень проекта**. Перейдите в неё и продолжайте с шага 1.2. В примерах ниже новая копия находится в `D:\Coding\sverka`; для существующей папки `D:\Coding\Hackathon` используйте свой путь.

#### Установите Git в Windows

Откройте меню «Пуск», найдите **PowerShell**, запустите обычное окно и проверьте:

```powershell
git --version
```

Если появилась версия, переходите к клонированию. Если команда не найдена, установите Git одним из способов:

- Через WinGet: `winget install --exact --id Git.Git --source winget`.
- Через [официальный установщик Git for Windows](https://git-scm.com/install/windows). В установщике оставьте доступ Git из командной строки и компонент Git Credential Manager.

После установки **закройте PowerShell и откройте новое окно**, затем повторите `git --version`: новое окно получает обновлённый `PATH` — список папок, где Windows ищет команды.

Если команда `winget` тоже не найдена, используйте обычный установщик по ссылке. WinGet поставляется через приложение Microsoft **App Installer / «Установщик приложений»**; [инструкция Microsoft](https://learn.microsoft.com/en-us/windows/package-manager/winget/) описывает его установку.

#### Авторизация GitHub для Git в Windows

Репозиторий приватный. Войдите в GitHub в браузере и откройте [E1ZY/sverka](https://github.com/E1ZY/sverka). Если видите 404, проверьте аккаунт и попросите владельца предоставить доступ; приглашение нужно принять. Одного знания ссылки для приватного репозитория недостаточно.

При первом HTTPS-клонировании Git Credential Manager может открыть окно входа. Выберите вход через браузер и авторизуйтесь **аккаунтом, которому предоставлен доступ**; при необходимости пройдите двухфакторную проверку. Git for Windows включает этот механизм. Подробности — в [инструкции GitHub по авторизации Git](https://docs.github.com/en/get-started/git-basics/caching-your-github-credentials-in-git).

#### Склонируйте проект через PowerShell

Сначала выберите папку, в которой у вас хранятся проекты, и определите её полный путь. Например, это может быть `D:\Coding` или `E:\Projects`. Путь можно скопировать из адресной строки Проводника Windows.

В командах ниже **замените `D:\Coding` своим путём в обеих первых строках**. Сохраните кавычки, особенно если в пути есть пробелы. Внутри выбранной папки Git сам создаст подпапку `sverka`: например, для `E:\Projects` проект окажется в `E:\Projects\sverka`.

Выполните команды в **PowerShell Windows**. Первая создаст папку для проектов, если её ещё нет, вторая перейдёт в неё:

```powershell
New-Item -ItemType Directory -Force 'D:\Coding'
Set-Location 'D:\Coding'
git clone https://github.com/E1ZY/sverka.git
Set-Location '.\sverka'
Get-ChildItem
```

`git clone` скачивает проект и создаёт папку `sverka`. При запросе авторизации выполните вход через браузер, описанный выше, затем дождитесь завершения команды. После `Get-ChildItem` должны быть видны `README.md`, `requirements.txt`, `Dockerfile`, `compose.yaml`, `app`, `frontend` и `scripts`. Дальше выполняйте шаги 1.2–1.7 из этой папки. Общая [инструкция по клонированию GitHub](https://docs.github.com/en/repositories/creating-and-managing-repositories/cloning-a-repository) показывает, где скопировать HTTPS-ссылку.

Частые ошибки:

| Сообщение | Что проверить |
|---|---|
| `git is not recognized` / «git не является командой» | Установку Git и новое окно PowerShell после установки. |
| `Repository not found` | Правильность ссылки, доступ к приватному репозиторию и аккаунт, выбранный при входе Git. |
| `destination path ... already exists` | Папка уже существует. Откройте её и проверьте содержимое или выберите другую папку для новой копии. |

Если репозиторий открывается в браузере, но Git всё равно отвечает `Repository not found`, он может использовать ранее сохранённый другой аккаунт. Проверьте запись GitHub в **Панель управления → Учётные записи пользователей → Диспетчер учётных данных**. Для повторной авторизации можно удалить именно эту сохранённую запись и повторить клонирование; порядок описан в приведённой выше инструкции GitHub по авторизации.

#### Альтернатива для Windows: клонирование через GitHub CLI

GitHub CLI предоставляет команду `gh`: через неё можно войти в GitHub и склонировать приватный репозиторий. Для клонирования также нужен Git из шага выше. Если вы уже скачали проект через `git clone`, переходите к шагу 1.2.

В **PowerShell Windows** проверьте наличие CLI:

```powershell
gh --version
```

Если команда не найдена, установите GitHub CLI:

```powershell
winget install --exact --id GitHub.cli --source winget
```

Без WinGet используйте Windows-установщик `.msi` из [официальных релизов GitHub CLI](https://github.com/cli/cli/releases/latest). После установки **закройте PowerShell и откройте новое окно**, затем повторите `gh --version`.

Войдите аккаунтом, которому предоставлен доступ к [E1ZY/sverka](https://github.com/E1ZY/sverka):

```powershell
gh auth login --hostname github.com --git-protocol https --web
```

CLI покажет одноразовый код и откроет браузер. Введите код на указанной странице и завершите вход; при вопросе об авторизации Git подтвердите её. Затем проверьте аккаунт, настройте Git и убедитесь, что репозиторий доступен:

```powershell
gh auth status
gh auth setup-git --hostname github.com
gh repo view E1ZY/sverka
```

После успешной проверки склонируйте проект. **Замените `D:\Coding` своим путём в обеих первых строках**:

```powershell
New-Item -ItemType Directory -Force 'D:\Coding'
Set-Location 'D:\Coding'
gh repo clone E1ZY/sverka
Set-Location '.\sverka'
Get-ChildItem
```

`gh repo clone E1ZY/sverka` создаст подпапку `sverka` в выбранном каталоге. Продолжайте с шага 1.2 из этой папки. Если `gh repo view` или клонирование сообщает об отсутствии доступа, проверьте аккаунт через `gh auth status`, принятие приглашения и повторите вход нужным аккаунтом. Справочники: [`gh auth login`](https://cli.github.com/manual/gh_auth_login) и [`gh repo clone`](https://cli.github.com/manual/gh_repo_clone).

#### Альтернатива для Windows: ZIP через браузер

Откройте репозиторий под аккаунтом с доступом, нажмите **Code → Download ZIP**, распакуйте архив и откройте полученную папку. ZIP достаточно для сборки и запуска; для него Git не обязателен. Если после распаковки внутри находится ещё одна папка `sverka-main`, корнем проекта будет она — там, где лежит `compose.yaml`.

### 1.2. Сначала проверьте установленные инструменты

В **PowerShell**, из корня проекта:

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\scripts\check_dependencies.ps1
```

Скрипт работает даже без Python. Он отдельно проверяет наличие `py` в `PATH` и запуск `py -3.12 --version`, показывает версии и пути к Python, pip, Node.js и npm, проверяет доступность `venv`, а для отсутствующих или неподходящих инструментов выводит подсказки по установке. `OK` означает успешную проверку, `ERROR` — проблему, которую нужно исправить, `WARN` — необязательный компонент. Отсутствующий или неработающий `py` даёт `WARN`: при наличии подходящего Python можно использовать его полный путь. Код завершения `0` означает, что обязательные проверки прошли, `1` — есть ошибки.

Проверка ничего не устанавливает, не скачивает и не меняет системные настройки. Базовый режим проверяет **инструменты сборки**; готовность самого проекта проверяется флагом `-Project` на шаге 1.7. Скрипт сначала использует существующую `.venv`, затем ищет установленный Python. При необходимости путь можно указать явно:

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\scripts\check_dependencies.ps1 -PythonExe 'C:\путь\к\python.exe'
```

В последнем примере замените путь своим. Для машинного отчёта есть флаг `-Json`.

### 1.3. Если инструментов нет: установите их

**Python.** При наличии WinGet выполните в PowerShell:

```powershell
winget install --exact --id Python.Python.3.12
```

Можно использовать [официальную страницу Python для Windows](https://www.python.org/downloads/windows/): выбирайте Python **3.12 x64**, а в обычном установщике оставьте включёнными `pip`, launcher и добавление Python в `PATH`. Описание установщиков и launcher есть в [документации Python 3.12](https://docs.python.org/3.12/using/windows.html). Если используется новый Python Install Manager, установите нужную версию командой `py install 3.12` и затем проверьте её командой ниже; работа manager описана в [актуальной документации Python для Windows](https://docs.python.org/3/using/windows.html).

После установки откройте **новое окно PowerShell** и проверьте:

```powershell
py -3.12 --version
py -3.12 -m pip --version
```

Ожидается Python `3.12.x`. Если pip отсутствует:

```powershell
py -3.12 -m ensurepip --upgrade
```

Если `py` не найден, включите компонент **Python Launcher** в установщике Python 3.12 либо установите **Python Install Manager**, затем откройте новое окно PowerShell. Если `py` найден, но `py -3.12 --version` сообщает об отсутствии нужной версии, установите Python 3.12 x64 способом выше; для Python Install Manager выполните `py install 3.12`.

Если `python --version` уже показывает **3.12.x**, вместо `py -3.12` можно использовать `python`. Также можно запускать найденный диагностикой интерпретатор по полному пути: например, `& 'C:\путь\к\python.exe' -m venv .venv` вместо команды создания окружения на шаге 1.4. Если команда `python` открывает Microsoft Store, используйте рабочий `py -3.12` или полный путь: сам по себе Store alias ещё не означает установленный Python.

**Node.js и npm.** Установите их одной командой:

```powershell
winget install --exact --id OpenJS.NodeJS.LTS
```

Без WinGet скачайте **Windows Installer (.msi), LTS** с [официального сайта Node.js](https://nodejs.org/en/download). Оставьте включёнными компоненты **npm package manager** и добавление в `PATH`. npm поставляется вместе с Node.js; [инструкция npm](https://docs.npmjs.com/downloading-and-installing-node-js-and-npm/) описывает этот способ установки.

В **новом окне PowerShell** проверьте:

```powershell
node --version
npm.cmd --version
```

Ожидаются Node.js `22.x` или новее и npm `9.x` или новее. Уже установленный Node.js `20.19+` тоже подходит. Если npm не найден или версия слишком старая, восстановите/обновите установку Node.js с компонентом npm. В командах для Windows ниже используется `npm.cmd`, чтобы PowerShell не блокировал запуск `npm.ps1` своей политикой исполнения.

**Git.** Установка описана в шаге 1.1 этого маршрута; она нужна при клонировании, но не при работе с ZIP. После установки недостающих инструментов вернитесь в корень проекта и повторите диагностику из шага 1.2.

### 1.4. Создайте Python-окружение и установите пакеты

Все дальнейшие команды этого раздела выполняются в **PowerShell Windows**, из корня проекта:

```powershell
py -3.12 -m venv .venv
.\.venv\Scripts\python.exe -m pip install --upgrade pip
.\.venv\Scripts\python.exe -m pip install -r requirements.txt -c constraints.txt
```

`.venv` — отдельное окружение проекта. Активация не обязательна: команды явно используют его Python, чтобы пакеты попали в нужное место. Не переходите к запуску, если `pip install` завершился ошибкой. При сообщениях о несовместимых wheel сначала проверьте, что выбран именно Python 3.12 x64.

### 1.5. Подготовьте OCR

```powershell
.\.venv\Scripts\python.exe scripts/setup_ocr.py
```

Скрипт скачает открытые языковые модели `eng` и `rus` в `.runtime/tessdata` и проверит их SHA-256. Повторный запуск использует уже проверенные файлы. Для этого шага нужен интернет; документы пользователя никуда не отправляются.

### 1.6. Соберите интерфейс

```powershell
Set-Location frontend
npm.cmd ci
npm.cmd run build
Set-Location ..
```

`npm ci` устанавливает точные зависимости из lock-файла, `npm run build` создаёт готовый интерфейс в `frontend/dist`. После сборки Node.js не участвует в обработке документов. При запуске через `scripts/start.ps1` изменения интерфейса обнаруживаются и пересобираются автоматически. Для запуска напрямую через Python сборку нужно повторять вручную.

### 1.7. Проверьте готовность и запустите

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\scripts\check_dependencies.ps1 -Project
```

Дополнительная проверка ищет `.venv`, сверяет Python-пакеты с `requirements.txt`, выполняет `pip check`, проверяет загрузку библиотек/DLL, инициализацию OCR с `rus+eng` и наличие собранного интерфейса. При `ERROR` выполните указанную подсказку и повторите проверку.

Запуск из корня проекта:

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\scripts\start.ps1
```

`start.ps1` перед запуском сравнивает содержимое исходников, стилей, ресурсов и настроек интерфейса с последней успешной сборкой. Если файлы изменены, добавлены или удалены либо готовая сборка отсутствует или повреждена, скрипт выполняет `npm.cmd run build` из `frontend`. Если сборка актуальна, пересборка пропускается и npm не требуется. При ошибке сборки сервер не запускается: исправьте указанную ошибку и повторите запуск. Первый запуск обновлённого скрипта также пересобирает интерфейс один раз, чтобы сохранить его состояние.

`-ExecutionPolicy Bypass` действует только для запущенного процесса PowerShell. Если запуск `.ps1` в вашей системе разрешён, достаточно `.\scripts\start.ps1`. Альтернатива напрямую через Python (без автоматической пересборки интерфейса):

```powershell
.\.venv\Scripts\python.exe -m uvicorn app.main:app --host 127.0.0.1 --port 8000
```

Оставьте терминал работающим и откройте в браузере Windows **http://127.0.0.1:8000**. Проверка готовности API: **http://127.0.0.1:8000/api/health**, документация API: **http://127.0.0.1:8000/docs**. В интерфейсе откройте «Примеры проверок» и запустите исходный комплект или «Проверить все примеры (31)».

Остановка — **Ctrl+C** в терминале сервера. Следующий запуск — та же команда `start.ps1`; повторная установка пакетов не нужна. Документы и SQLite хранятся в `data/`. Для этого режима используйте один API-процесс, без `--workers` и `--reload`.

**Как запустить обновлённую версию после `git pull`:** остановите сервер через **Ctrl+C** и выполните из корня проекта:

```powershell
git pull --ff-only
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\scripts\start.ps1
```

Затем обновите страницу через **Ctrl+F5**. Если изменились `package.json` или `package-lock.json` в `frontend`, перед запуском обновите npm-зависимости командой `npm.cmd --prefix frontend ci` из корня проекта. Если изменились `requirements.txt` или `constraints.txt`, повторите установку Python-пакетов из шага 1.4. Папка `frontend/dist` не хранится в Git; её актуальность при запуске обеспечивает `start.ps1`.

### 1.8. Если локальный запуск не получился

| Проблема | Действие |
|---|---|
| После установки команда не найдена | Откройте новое окно PowerShell; повторите диагностику, проверьте путь к установленному инструменту. |
| Python другой версии или 32-bit | Установите Python 3.12 x64 и создавайте `.venv` именно им. Версию существующего окружения покажет диагностика. |
| `No module named ...` | Используйте `.venv\Scripts\python.exe` и установите `requirements.txt` с `constraints.txt` в это окружение. |
| `npm.ps1 cannot be loaded` | Выполняйте `npm.cmd ci` и `npm.cmd run build`. |
| OCR не находит языки | Повторите шаг 1.5; если задан `TESSDATA_PREFIX`, он должен указывать на папку с моделями `eng` и `rus`. |
| Интерфейс не собран | Запустите `start.ps1`: он выполнит сборку автоматически. Если не установлены npm-зависимости, выполните шаг 1.6. |
| После `git pull` виден старый интерфейс | Остановите прежний сервер и повторно запустите `start.ps1` по инструкции в конце шага 1.7, затем нажмите Ctrl+F5. |
| Порт 8000 занят | Остановите предыдущий сервер через Ctrl+C или контейнеры этого проекта, прежде чем запускать второй экземпляр. |

Для разработки интерфейса можно запустить API на порту 8000 и `npm.cmd run dev` из `frontend`: Vite проксирует `/api` в локальный backend. Для обычного использования достаточно production-сборки выше.

## 2. Запуск через Docker Desktop и WSL 2 с нуля

**WSL** позволяет работать с Ubuntu внутри Windows. **Docker Desktop** запускает контейнеры и предоставляет команду `docker` этой Ubuntu. **Docker Compose** по файлу `compose.yaml` поднимает три сервиса проекта: `db` (PostgreSQL 16), `api` (приложение) и `worker` (обработка документов). Python, Node.js/npm и OCR устанавливаются внутри образов при сборке.

Этот маршрут можно пройти самостоятельно, начиная с установки WSL. Git и авторизация GitHub настраиваются внутри Ubuntu; новая копия проекта будет находиться в `~/projects/sverka`. Для Linux-команд используйте терминал Ubuntu, для установки WSL и Docker Desktop — Windows, как указано в каждом шаге.

Для Docker Desktop нужны поддерживаемая версия Windows, WSL 2, включённая аппаратная виртуализация и как минимум **8 ГБ системной RAM**; актуальные требования приведены на [официальной странице установки](https://docs.docker.com/desktop/setup/install/windows-install/). Для первой сборки нужен интернет и место на диске под Linux, образы и зависимости.

Состояние виртуализации можно посмотреть в Windows: **Ctrl+Shift+Esc → Производительность → ЦП → Виртуализация**. Если она отключена, включите VT-x / AMD-V в BIOS/UEFI по инструкции производителя компьютера.

### 2.1. Установите Ubuntu в WSL

В Windows откройте **PowerShell от имени администратора**: «Пуск» → PowerShell → «Запуск от имени администратора».

```powershell
wsl --install -d Ubuntu
```

Дождитесь завершения и **перезагрузите Windows**, если это предложено. Затем откройте **Ubuntu** из меню «Пуск». При первом запуске создайте Linux-пользователя и пароль; при вводе пароля символы не отображаются — это нормально. Этот пользователь относится к Ubuntu.

Снова в **PowerShell Windows**:

```powershell
wsl --update
wsl --list --verbose
```

В таблице рядом с Ubuntu должна быть `VERSION 2`; `Stopped` в колонке состояния допустим, когда терминал закрыт. Если указана версия 1:

```powershell
wsl --set-version Ubuntu 2
```

Подставьте точное имя из колонки `NAME`, если оно отличается, например `Ubuntu-24.04`. Установка и команды описаны в [руководстве Microsoft по WSL](https://learn.microsoft.com/en-us/windows/wsl/install) и [справочнике команд WSL](https://learn.microsoft.com/en-us/windows/wsl/basic-commands).

### 2.2. Установите и настройте Docker Desktop

1. Скачайте установщик **Docker Desktop for Windows** с [официальной страницы](https://docs.docker.com/desktop/setup/install/windows-install/).
2. Запустите его и выберите backend **WSL 2**, если установщик предлагает выбор. Завершите установку и требуемую перезагрузку.
3. Откройте **Docker Desktop** из меню «Пуск» и дождитесь готовности движка.
4. В **Settings → General** выберите WSL 2 backend / **Use WSL 2 based engine**, если настройка отображается.
5. В **Settings → Resources → WSL Integration** включите интеграцию с вашей Ubuntu и примените изменения.

Команда `docker` в Ubuntu появляется через эту интеграцию. Если раздел WSL Integration отсутствует, проверьте Linux-container mode: в меню Docker может быть команда **Switch to Linux containers**. Детали — в [документации Docker по WSL 2](https://docs.docker.com/desktop/features/wsl/).

### 2.3. Проверьте Docker из Ubuntu

Откройте **Ubuntu** через «Пуск» или выполните в PowerShell `wsl -d Ubuntu`. Дальнейшие команды этого раздела выполняются **в Ubuntu**:

```bash
docker --version
docker compose version
docker info
```

Первые две команды должны показать версии, последняя — сведения и о клиенте, и о сервере Docker. Если `docker info` сообщает, что не может подключиться к daemon, откройте Docker Desktop в Windows и дождитесь готовности. При `docker: command not found` вернитесь к WSL Integration, включите нужную Ubuntu и откройте её терминал заново.

### 2.4. Установите Git и GitHub CLI внутри Ubuntu

Откройте **Ubuntu**. Все команды этого подраздела выполняются здесь. Сначала установите Git и инструменты для подключения официального репозитория GitHub CLI:

```bash
sudo apt update
sudo apt install --yes git curl ca-certificates
```

При запросе `sudo` введите пароль Linux-пользователя, созданного при установке Ubuntu. Подключите официальный источник пакета `gh`:

```bash
gh_keyring_tmp=$(mktemp)
curl --fail --silent --show-error --location https://cli.github.com/packages/githubcli-archive-keyring.gpg --output "$gh_keyring_tmp" &&
sudo install -D -m 0644 "$gh_keyring_tmp" /etc/apt/keyrings/githubcli-archive-keyring.gpg
```

После успешной загрузки ключа добавьте источник и установите CLI:

```bash
printf 'deb [arch=%s signed-by=/etc/apt/keyrings/githubcli-archive-keyring.gpg] https://cli.github.com/packages stable main\n' "$(dpkg --print-architecture)" | sudo tee /etc/apt/sources.list.d/github-cli.list > /dev/null
sudo apt update
sudo apt install --yes gh
git --version
gh --version
```

Обе последние команды должны показать версии. Для `gh` используется [официальный APT-репозиторий GitHub CLI](https://github.com/cli/cli/blob/trunk/docs/install_linux.md#debian): сопровождающие CLI предупреждают о проблемах старых пакетов 2.45/2.46 из репозиториев Ubuntu. Если установка завершилась ошибкой, исправьте её перед следующим шагом.

### 2.5. Авторизуйтесь в GitHub из Ubuntu

Репозиторий приватный. В браузере Windows войдите в GitHub и убедитесь, что открывается [E1ZY/sverka](https://github.com/E1ZY/sverka). Если видите 404, проверьте аккаунт, доступ и принятие приглашения владельца.

В **терминале Ubuntu** запустите отдельную авторизацию для Git в Linux:

```bash
gh auth login --hostname github.com --git-protocol https --web
```

Выберите вход через браузер и подтвердите использование учётной записи GitHub для Git, если появится такой вопрос. CLI покажет одноразовый код и адрес входа. Откройте показанную страницу в браузере Windows, введите код и завершите авторизацию аккаунтом с доступом к репозиторию. Если браузер из WSL не открылся автоматически, перейдите на показанный адрес вручную; обычно это `https://github.com/login/device`.

Когда терминал подтвердит успешный вход, проверьте аккаунт и настройте Git на использование этих учётных данных:

```bash
gh auth status
gh auth setup-git --hostname github.com
gh repo view E1ZY/sverka
```

Последняя команда должна показать сведения о репозитории. При ошибке доступа проверьте аккаунт в `gh auth status` и повторите вход нужной учётной записью. Подробности — в справочниках [`gh auth login`](https://cli.github.com/manual/gh_auth_login) и [`gh auth setup-git`](https://cli.github.com/manual/gh_auth_setup-git).

### 2.6. Склонируйте репозиторий через GitHub CLI в файловую систему WSL

После авторизации на шаге 2.5 в **Ubuntu** создайте папку для проектов и скачайте репозиторий через `gh`:

```bash
mkdir -p ~/projects
cd ~/projects
gh repo clone E1ZY/sverka
cd sverka
pwd
ls README.md compose.yaml Dockerfile app frontend scripts
```

Команда [`gh repo clone`](https://cli.github.com/manual/gh_repo_clone) создаёт каталог `sverka`, используя настроенную на шаге 2.5 авторизацию и HTTPS. `pwd` должен показать `/home/<ваш-linux-пользователь>/projects/sverka`. Это корень проекта для всех дальнейших Docker-команд. Хранение проекта в файловой системе Linux соответствует [рекомендации Microsoft для работы из WSL](https://learn.microsoft.com/en-us/windows/wsl/filesystems). Если копия уже есть внутри Ubuntu, перейдите в её корень вместо повторного клонирования.

При `Repository not found` вернитесь к проверке доступа на шаге 2.5. При `destination path ... already exists` проверьте существующую папку или выберите другое имя для новой копии. Для просмотра этой папки в Проводнике Windows из Ubuntu можно выполнить `explorer.exe .`.

### 2.7. Настройте VS Code для работы с WSL (необязательно)

VS Code можно использовать как редактор Windows, подключённый к Ubuntu: файлы проекта, Git и встроенный терминал будут работать в WSL. Настройка редактора необязательна для запуска приложения через Compose.

#### Установите редактор в Windows и расширение WSL

1. Скачайте **VS Code User Installer для Windows** с [официального сайта](https://code.visualstudio.com/docs/setup/windows). Запустите установщик и оставьте включённым **Add to PATH**.
2. Откройте VS Code в Windows. Нажмите **Ctrl+Shift+X**, найдите расширение **WSL** от **Microsoft** и установите его. Идентификатор расширения — `ms-vscode-remote.remote-wsl`; [прямая ссылка в Marketplace](https://marketplace.visualstudio.com/items?itemName=ms-vscode-remote.remote-wsl).
3. После установки редактора закройте старое окно терминала Ubuntu и откройте новое, чтобы обновился `PATH`.

Такое расположение редактора и расширения соответствует [инструкции Microsoft по VS Code и WSL](https://learn.microsoft.com/en-us/windows/wsl/tutorials/wsl-vscode).

#### Откройте Linux-копию проекта

В **терминале Ubuntu**:

```bash
cd ~/projects/sverka
code .
```

При первом подключении загрузится VS Code Server для Ubuntu; дождитесь завершения, для этого нужен интернет. Откроется окно редактора с папками `app`, `frontend` и `scripts`.

В левом нижнем углу должен появиться индикатор **WSL: Ubuntu** или имя вашей Ubuntu. Он подтверждает, что окно подключено к Linux. Подробности подключения описаны в [руководстве VS Code по WSL](https://code.visualstudio.com/docs/remote/wsl).

Открыть подключение можно и из самого редактора: **Ctrl+Shift+P → WSL: Connect to WSL using Distro**, выбрать Ubuntu, затем **File → Open Folder** и папку `/home/<ваш-linux-пользователь>/projects/sverka`. Если папка уже открыта в обычном окне, используйте **WSL: Reopen Folder in WSL** из той же палитры команд.

#### Проверьте встроенный терминал и Git

В подключённом окне выберите **Terminal → New Terminal** и выполните:

```bash
pwd
uname -s
command -v git
git status
docker compose version
```

Ожидается путь `/home/<ваш-linux-пользователь>/projects/sverka`, система `Linux`, путь к Git вида `/usr/bin/git`, состояние репозитория и версия Compose. Для Git используется авторизация, настроенная в Ubuntu на шаге 2.5. Встроенный [терминал VS Code в WSL](https://code.visualstudio.com/docs/remote/wsl-tutorial#integrated-terminal) позволяет дальше выполнять Docker-команды прямо в редакторе.

Расширения для работы с кодом устанавливайте из этого WSL-окна. Если редактор предлагает **Install in WSL: Ubuntu**, выберите установку в Ubuntu; установленные расширения можно проверить в группе WSL на панели Extensions. При этом Linux-окружение редактора и контейнер приложения — отдельные среды: Python и пакеты текущего Docker-маршрута устанавливаются при сборке образа.

#### Дальнейшая работа и частые проблемы

Сохраните изменения файлов через **Ctrl+S** и продолжайте с шага 2.8 в терминале VS Code. После изменений исходников используйте команду пересборки из шага 2.10. После закрытия редактора папку можно снова открыть из Ubuntu командой `cd ~/projects/sverka`, затем `code .`.

| Проблема | Что сделать |
|---|---|
| `code: command not found` | Проверить установку VS Code в Windows и Add to PATH, затем открыть новое окно Ubuntu. |

### 2.8. Настройте окружение и соберите контейнеры

Выполните команды **в Ubuntu, из корня проекта** — подойдёт и встроенный терминал VS Code, подключённый к WSL. Создайте `.env` из примера, сохранив существующий файл, если он уже есть:

```bash
if [ ! -f .env ]; then cp .env.example .env; fi
docker compose config --quiet
docker compose up --build -d --wait
docker compose ps
```

`.env` задаёт локальный пароль PostgreSQL. Его можно изменить **до первого запуска**; используйте URL-safe символы, например латинские буквы и цифры. Существующий пароль уже созданной БД не изменяется простым редактированием `.env`.

`--build` собирает образ, `-d` оставляет контейнеры работать в фоне, `--wait` ждёт их готовности. Первая сборка может занять несколько минут: скачиваются базовые образы, Python/npm-пакеты и OCR-компоненты. После успешного завершения в `docker compose ps` сервисы `db` и `api` должны быть healthy, а `worker` — запущен. Команда описана в [справочнике Docker Compose](https://docs.docker.com/reference/cli/docker/compose/up/).

### 2.9. Откройте приложение в Windows: порт уже опубликован

В `compose.yaml` у сервиса `api` уже настроено сопоставление порта:

```yaml
ports:
  - "127.0.0.1:8000:8000"
```

Формат записи — `адрес хоста:порт хоста:порт контейнера`. При выбранном в этом гайде Docker Desktop с WSL 2 порт 8000 контейнера доступен на `127.0.0.1:8000` Windows. Docker Desktop перенаправляет запросы с Windows в контейнер — это описано в [документации по публикации портов](https://docs.docker.com/desktop/features/networking/#how-exposed-ports-work). Внутри контейнера Uvicorn слушает `0.0.0.0:8000`; доступ с хоста ограничен этим компьютером адресом `127.0.0.1`.

В обычном **браузере Windows** откройте:

- **http://127.0.0.1:8000** — интерфейс;
- **http://127.0.0.1:8000/api/health** — проверка API, поле `status` должно быть `ok`;
- **http://127.0.0.1:8000/docs** — Swagger API.

Compose запускает сервисы; страницу в браузере откройте вручную после завершения сборки. Проверить соединение из **PowerShell Windows** можно так:

```powershell
Invoke-RestMethod http://127.0.0.1:8000/api/health
```

В ответе должно быть `status: ok`. Если страница недоступна, в терминале Ubuntu проверьте `docker compose ps` и `docker compose logs --tail=100 api`; сервис `api` должен быть healthy.

Нажмите «Примеры проверок» → «Исходный комплект задания» → «Запустить проверку» или «Проверить все примеры (31)». При дальнейшей работе оставляйте Docker Desktop запущенным; терминал Ubuntu после запуска с `-d` можно закрыть.

### 2.10. Остановка, повторный запуск и обновление

Эти команды выполняются **в Ubuntu, из той же папки проекта**:

| Задача | Команда |
|---|---|
| Посмотреть состояние | `docker compose ps` |
| Посмотреть последние сообщения и следить за новыми | `docker compose logs --tail=100 -f api worker db` |
| Остановить проект | `docker compose stop` |
| Запустить проект снова | `docker compose up -d --wait` |
| Пересобрать после изменения исходников | `docker compose up --build -d --wait` |
| Остановить и удалить контейнеры и сеть, сохранив тома данных | `docker compose down` |

Ctrl+C в режиме просмотра логов останавливает только просмотр. Документы и PostgreSQL хранятся в именованных volumes `documents` и `postgres-data`. Обычный `stop` или `down` сохраняет их; флаг `--volumes` / `-v` у `down` удаляет тома вместе с данными. Подробности — в [справочнике `docker compose down`](https://docs.docker.com/reference/cli/docker/compose/down/).

Данные Docker и локальная SQLite из раздела 1 хранятся отдельно. Переключение способа запуска само по себе не переносит историю проверок. API опубликован только на `127.0.0.1`; для сетевой публикации MVP потребуются отдельные авторизация и защищённый шлюз. Эталонный XLSX и README исходного набора исключены из Docker build context.

### 2.11. Частые проблемы Docker / WSL

| Проблема | Что сделать |
|---|---|
| `docker: command not found` в Ubuntu | Запустить Docker Desktop, включить Ubuntu в WSL Integration, открыть терминал Ubuntu заново. |
| `Cannot connect to the Docker daemon` | Дождаться готовности Docker Desktop и повторить `docker info`. |
| `no configuration file provided` | Перейти в папку с `compose.yaml`, проверить путь командой `pwd`. |
| `Repository not found` при клонировании | Проверить аккаунт через `gh auth status` и доступ командой `gh repo view E1ZY/sverka`; повторить шаг 2.5. |
| Порт 8000 уже занят | Остановить локальный Python-сервер через Ctrl+C или другой экземпляр проекта. |
| Ошибка виртуализации / WSL 2 | Проверить требования Docker, включение виртуализации в BIOS/UEFI и WSL 2; выполнить `wsl --update` в PowerShell Windows. |
| Ошибка скачивания образов или пакетов | Проверить интернет и настройки сети/proxy Docker Desktop, затем повторить сборку; для деталей открыть `docker compose logs`. |
| `password authentication failed` после изменения `.env` | Для существующего тома вернуть пароль, с которым БД была создана; смена `.env` не меняет пароль внутри PostgreSQL. |

Успех тестового сценария означает ожидаемое поведение программы: в самих документах при этом могут быть расхождения. Сценарии 20–24 отмечены как ограничения MVP. Кейс 28 показывает ожидаемый отказ загрузки, без запуска сверки сумм.

После обновления исходников при запуске без Docker перезапустите локальный сервер через `scripts/start.ps1`: он автоматически пересоберёт изменённый интерфейс. Если изменился список npm-зависимостей, сначала выполните `npm.cmd --prefix frontend ci` из корня проекта — полная последовательность приведена в конце шага 1.7. Для Docker пересоберите образ командой `docker compose up --build -d --wait` из папки проекта. Затем обновите страницу через Ctrl+F5. Каталог и документы доступны обоими способами запуска. Эталон сравнивается с готовым результатом; расчётный пайплайн его не читает.

**Все кейсы одной кнопкой:** откройте «Примеры проверок» и нажмите «Проверить все примеры (31)». Поиск и фильтры не ограничивают общий прогон: запускается весь установленный каталог, включая исходный комплект задания. На вкладке «Все примеры» видны прогресс, совпадения с эталонами, известные ограничения и новые ошибки; из каждой строки можно открыть соответствующую проверку. Повреждённый XLSX учитывается как успешный тест ожидаемого отказа загрузки. Окно можно закрыть, а страницу обновить: задания продолжают выполняться worker, последний прогон сохраняется в БД. Демонстрационный комплект заявлен полным для верхних статей. Названия используются только для выбора файлов демонстрации; извлечение и расчёты не зависят от имён. При запуске через каталог результат дополнительно сравнивается с `demo/expected.json` после завершения расчёта.

CSV содержит сводку показателей, JSON — полный результат с источниками и замечаниями.

### 2. Собственный или неполный комплект

Чтобы очистить сохранённые проверки, нажмите значок корзины рядом с «Последние проверки» или **«Очистить»** в общем списке. Перед удалением появится предупреждение с количеством проверок. Для удаления одной проверки используйте корзину в её строке или кнопку удаления внутри открытой проверки: предупреждение покажет её название. «Отмена», крестик и Escape закрывают его без удаления. После подтверждения удаляются загруженные копии документов, результаты и история запусков этих проверок; исходные файлы на компьютере сохраняются. Выполняющиеся проверки остаются. Очистка охватывает список последних проверок независимо от поискового фильтра.

Пока проверок ещё нет, стартовый экран предлагает **«Пройти учебный пример»** на готовом комплекте или **«Загрузить свои документы»**. После появления проверок обучение можно снова открыть по кнопке **«Учебный пример»** в шапке.

Краткий обзор формы доступен по кнопке **«Показать подсказки»** внутри новой проверки, а после появления проверок — также по кнопке **«Как сделать проверку»** в шапке. Подсказки по очереди выделят загрузку КФЗ, параметры сверки, первичные документы, полноту комплекта и запуск. Можно заполнять форму во время обучения или пройти шаги без документов. Кнопки «Назад» и «Далее» переключают шаги, Escape закрывает подсказки. Завершение обучения сохраняет заполненные поля и не запускает сверку автоматически.

Отдельная кнопка **«Учебный пример»** запускает практический туториал на готовом комплекте документов. Скачайте учебный архив прямо из подсказки и распакуйте его: ZIP содержит папки `report` с КФЗ и `primary` с 22 первичными документами. Обучение состоит из 11 шагов: выбор КФЗ, проверка параметров строки, выбор первичных документов, подтверждение полноты, запуск сверки, ожидание расчёта, выбор фильтра расхождений, открытие статьи, просмотр КФЗ, просмотр первичного документа и сравнение сумм. Документы выбираются через ту же форму, что и в обычной проверке. **«Далее» недоступна, пока текущее задание не выполнено**; неверный ответ на последнем шаге также блокирует завершение. При просмотре источника подсветка открывает сам подтверждающий фрагмент, а не заголовок файла. В конце запускается короткая анимация конфетти; кнопка «Ещё конфетти» повторяет её. Можно вернуться назад или выйти через крестик, Escape либо «Выйти» — выход не считается прохождением. Учебная проверка создаётся отдельно и остаётся в списке проверок.

После верного ответа и нажатия **«Завершить обучение»** появляется поздравление с падающим конфетти. Эта короткая анимация работает и при включённом в системе уменьшении движения. Обзор формы из пяти шагов работает как прежде.

В учебном примере скан автоматически приближается к выделенной сумме. В подсказке крупно показаны сумма, этап, год и статья. Панель над документом позволяет менять масштаб, возвращаться **«К фрагменту»** и показывать лист целиком кнопкой **«Вся страница»**. Эти инструменты доступны и при обычном просмотре документов. Предпросмотр PDF загружается в повышенном разрешении, а на узком экране подсказка располагается рядом с выделенной суммой, не закрывая её.

Нажмите «Новая проверка» и выберите отчёт КФЗ (PDF, PNG или JPEG). После выбора файла приложение попробует заполнить номер договора, этап и даты периода. Проверьте найденные значения: любое поле можно исправить вручную. Отсутствующие, неоднозначные или неуверенно распознанные значения остаются пустыми с подсказкой. Ручные правки сохраняются, в том числе если распознавание ещё выполняется или выбран другой отчёт; прежние автоматические значения при замене или удалении КФЗ очищаются.

Даты подставляются только из явно указанного периода (диапазон дат, диапазон месяцев или один месяц), дата договора и один лишь год не используются. Если в КФЗ перечислено несколько разных этапов, выберите нужный вручную. Период сверки должен находиться внутри одного года. Распознавание выполняется локально; временная копия файла удаляется, проверка и задание обработки на этом шаге не создаются. При ошибке распознавания параметры можно заполнить вручную и продолжить.

Добавьте первичные документы PDF/DOCX/XLSX/PNG/JPEG и запустите сверку. В MVP профиль отчёта соответствует предоставленной 17-колоночной форме КФЗ.

Если полнота комплекта не подтверждена, система покажет подтверждённые промежуточные суммы со статусом «Недостаточно данных». Например, при отсутствии январской ведомости по зарплате статья 0200 и итог не будут помечены как ошибочные; ожидаемая полная сумма останется неизвестной. Обработка остальных файлов продолжится.

При наличии неоднозначных распознанных данных откройте документ и выберите «Уточнить данные». Можно изменить статью/сумму с обязательным основанием; API также поддерживает уточнение договора и периода. Создаётся событие аудита и новый запуск. Исходное извлечение и предыдущие результаты сохраняются. Это пользовательское уточнение, а не новое автоматическое доказательство: оно явно отмечается в результате.

## Архитектура и поток данных

```text
React → FastAPI → PostgreSQL / SQLite
                    ↓ постоянное задание Run
                  worker
                    ↓
  извлечение → нормализация → фильтрация → классификация → Decimal-сверка
                    ↓
  неизменяемый снимок результата + ссылки на фрагменты → React / JSON / CSV
```

| Модуль | Назначение |
|---|---|
| `app/main.py` | REST API, загрузки, просмотр оригиналов и страниц, экспорт, аудит уточнений |
| `app/db.py` | Case, Document, Run, Review; схема БД и сессии |
| `app/pipeline.py` | Постоянная очередь, аренда задания, прогресс, кеш извлечения и снимки запусков |
| `app/extractors.py` | PDF-текст и OCR, DOCX-таблицы, XLSX-регистры, профиль сетки КФЗ |
| `app/report_context.py` | Предварительное распознавание договора, этапа и периода КФЗ с проверкой неоднозначности и уверенности OCR |
| `app/ocr.py` | Сменный интерфейс локального OCR; Tesseract через tesserocr или CLI |
| `app/domain.py` | Чистое расчётное ядро без доступа к файлам, БД и эталону |
| `app/rules.json` | Версия правил классификации, колонки профиля КФЗ, непроверяемые подпоказатели |
| `frontend/src` | Рабочее пространство проверок, детализация расчётов и просмотр доказательств |

Факты и доказательства хранятся структурированным JSON в Document, а операции и расчёты — в снимке Run. Каждый факт имеет источник: нормализованный прямоугольник страницы, Excel-диапазон или DOCX-адрес. Снимок содержит версии пайплайна/правил, контекст, хеши файлов и применённые уточнения. Денежные значения сериализуются строками, расчёт выполняется через Decimal с ROUND_HALF_UP до копейки. Дельта — отчёт минус ожидаемое значение.

Дубли выявляются по SHA-256 и реквизитам: номер, дата, договор, контрагент, сумма. Конфликтующие версии с разными суммами исключаются из подтверждённого агрегата до проверки. Для зарплаты и взносов контролируется наличие единственного расчёта на каждый месяц. Пересечение периода не распределяется пропорционально автоматически.

Отсутствующие данные не превращаются в нули. Ошибка чтения/неоднозначная связь консервативно блокирует полное подтверждение агрегатов, поскольку нераспознанный документ может относиться к любой статье. В итоговом заключении всегда указываются границы проверки.

Тяжёлое извлечение выполняет worker. В PostgreSQL задание выбирается через `FOR UPDATE SKIP LOCKED`; локальный SQLite рассчитан на одного worker. Аренда обновляется при переходе к документу, истекает через 10 минут. Задание после прерывания подбирается повторно, максимум три попытки. Успешные извлечения кешируются; повторный запуск пересчитывает результат из фактов и снимка уточнений. Таблицы создаются автоматически; для последующих изменений схемы понадобятся миграции.

## Настройки

Переменные окружения читаются процессом при старте. Для прямого запуска `.env` автоматически не загружается: задайте переменные в shell. Compose читает `.env`; образец — `.env.example`.

| Переменная | Значение по умолчанию / назначение |
|---|---|
| `DATABASE_URL` | SQLite `data/audit.db`; Compose задаёт PostgreSQL |
| `DATA_DIR` | `data/`; оригиналы и локальная БД |
| `DEMO_DIR` | `task/data`; в контейнере `/demo` |
| `FIXTURES_DIR` | `cases/`; каталог, входные документы и эталоны синтетических кейсов |
| `EMBED_WORKER` | `true` локально; `false` для отдельного worker |
| `TESSDATA_PREFIX` | `.runtime/tessdata` для Windows tesserocr; Linux CLI использует системные модели |
| `TESSERACT_CMD` | Необязательный путь к CLI Tesseract |
| `POSTGRES_PASSWORD` | Локальный пароль Compose; при изменении используйте URL-safe символы |

Ограничения загрузки: 25 МБ на файл, 100 файлов на проверку, 50 страниц на PDF, распакованный DOCX/XLSX до 100 МБ. Ошибки файлов показываются отдельно. Внешние сервисы, API-ключи, GPU и облачная LLM не требуются.

## Проверки

```powershell
.\.venv\Scripts\python.exe -m pip install -r requirements-dev.txt -c constraints.txt
.\.venv\Scripts\python.exe -m pytest -q
Set-Location frontend
npm.cmd run build
Set-Location ..
```

`requirements-dev.txt` добавляет инструменты тестирования к пакетам приложения. Диагностику сборки можно проверить отдельно командой `.\.venv\Scripts\python.exe -m pytest tests/test_dependency_check.py -q`: её тесты имитируют отсутствующие инструменты, старые версии Node.js/npm и неподходящий Python, не меняя установленные программы. Скрипт проверен в Windows PowerShell 5.1; расширенная проверка `check_dependencies.ps1 -Project` на подготовленном окружении проходит все проверки.

Тесты проверяют полный комплект с OCR и независимым эталоном, точные адреса доказательств, независимость от имён файлов, пропущенный месяц, изменение суммы, повторный скан, конфликт версий, неполный комплект, повреждённый документ, отсутствующее значение отчёта, округление, API, экспорт и сохранение истории уточнений. XLSX с правильными ответами исходного задания используется только в тестах; тесты также проверяют соответствие ему `demo/expected.json`. JSON-эталоны исходного и синтетических кейсов читаются отдельным модулем сравнения после расчёта. Для тестирования полного комплекта нужен исходный каталог `task/data` и доступный локальный OCR.

Последний полный прогон на Windows с Python 3.12: **67 passed, 5 xfailed**, включая тесты диагностики инструментов. Production-сборка TypeScript/Vite успешна. ## Границы MVP

Профиль КФЗ поддерживает данную табличную форму и одну выбранную годовую строку на первой странице. Координаты сетки определяются по изображению, суммы не зашиты в код. Произвольные формы, повёрнутые/перспективно искажённые и низкокачественные сканы требуют дополнительных профилей и предобработки.

XLSX-парсер поддерживает структуры ведомостей/взносов этого набора. Он складывает исходные начисления и не использует пустой или устаревший кеш итоговой формулы. Универсальное вычисление Excel-формул не реализовано. Текстовые документы рассматриваются как одна денежная операция; документы с несколькими различными суммами требуют уточнения. Классификация основана на прозрачных смысловых правилах, сложные случаи получают статус проверки.
